# 架构改善建议报告

> 文档状态：定稿 | 阶段：质量审查 | 审查日期：2026-08-09

---

## 一、评审范围与总体结论

对 Astro Agent 核心架构的 9 大组成部分进行了深度评审：Agent 主循环、Crate 分层、状态管理、错误恢复、Provider 抽象、记忆系统、上下文管理、工具/Skills 系统、子 Agent 架构、人工接管。

**总体评分：**

| 组件 | 评定 | 核心问题 |
| ---- | ---- | ---- |
| Agent 主循环 | 存在缺陷 | 两份矛盾的循环定义；工具拒绝无反馈；无限循环保护缺失 |
| Crate 分层 | 需要改善 | 潜在循环依赖；agent-core 职责过重；硬依赖 Tauri AppHandle |
| 状态管理 | 需要改善 | AgentContext 两版矛盾；AgentState 枚举不完整；子 Agent 清理缺失 |
| 错误恢复 | 存在缺陷 | 崩溃恢复几乎未设计；"replay" 不可行；幂等性依赖不可靠 |
| Provider 抽象 | 设计良好 | 个别接口不统一；熔断器实现有 bug；流式恢复效果存疑 |
| 记忆系统 | 设计良好 | L5 与 L3 可合并；Weibull 衰减可延后；容量限制偏小 |
| 上下文管理 | 设计良好 | 三级压缩精良；TokenBudget 有竞态；重要性评分过简 |
| 工具/Skills 系统 | 需要改善 | 工具优先级语义反转（安全漏洞）；Tool trait 两版不一致 |
| 子 Agent + HumanGuard | 设计良好 | 审批超时计时起点需修正；白名单正则匹配 JSON 不可靠 |

## 二、P0 — 必须在编码前修复的架构缺陷

### 2.1 统一 Agent 主循环（消除双版本）

**问题**：agent-core 的 `run_agent_turn` 和 agent-runtime 的 `AgentExecutor::round_loop` 是两套逻辑不一致的主循环实现。工具并发策略、HumanGuard 集成、Pending 队列、自适应规划等行为完全不同。

**建议**：
- 删除 agent-core 中的 `run_agent_turn`，以 agent-runtime 的 `round_loop` 为唯一权威
- agent-core 只暴露 `build_request` / `parse_response` / `execute_tool_calls` 等纯函数
- 在 `round_loop` 中补充 `max_tool_rounds` 守卫（建议默认 25），接近上限时注入系统消息提醒 LLM 软着陆

### 2.2 修复工具优先级语义反转（安全漏洞）

**问题**：系统设计说"内置 > MCP > Skills"（内置最高），但详细设计中优先级数值为内置=0、MCP=5、WASM=10（数值越高越优先）。实际执行顺序是 WASM > MCP > 内置，恶意 MCP Server 可覆盖内置 `file_read`。

**建议**：
- 内置工具优先级最高且不可覆盖（`frozen = true`）
- MCP/WASM 工具必须带命名空间前缀（`mcp__server__tool_name`）
- ToolRegistry 注册时拒绝与内置工具同名的外部工具

### 2.3 HumanGuard 拒绝后注入上下文反馈

**问题**：用户拒绝工具调用后，仅 `continue` 跳过，不向 LLM 注入任何反馈。LLM 不知道被拒绝，可能重复尝试或基于错误假设继续推理。

**建议**：拒绝时注入 `ToolResult { is_error: true, output: "用户拒绝了此操作: <工具名>" }`，让 LLM 感知并调整策略。

### 2.4 解决 Crate 循环依赖风险

**问题**：agent-core 持有 `Arc<dyn TextClient>`（定义在 agent-providers），而文档暗示 agent-providers 可能依赖 agent-core 的 Message 类型，构成循环。

**建议**（三选一，推荐第一项）：
1. **提取 `agent-types` crate**：放所有跨 crate 共享类型（Message、ContentPart、ToolCall、TextClient trait 等），agent-core 和 agent-providers 都依赖它
2. 将 TextClient trait 上移到 agent-core，agent-providers 只做实现层
3. 确认 agent-providers 不依赖 agent-core，修正文档表述

### 2.5 统一 AgentContext 结构体

**问题**：03-Crate结构.md 和 01-agent-core详细设计.md 定义了两个几乎完全不同的 AgentContext，一个是 God Object 持有所有注册表，一个是精简的单轮上下文。

**建议**：拆分为两层：
- `AgentSession`：长生命周期，持有注册表引用（tools、skills、providers、supervisor）
- `TurnContext`：短生命周期，每轮构建，包含 message_history、model、system_prompt、token_budget

`AgentExecutor` 持有 `AgentSession`，每次 `round_loop` 迭代构建临时 `TurnContext`。

### 2.6 修复熔断器 CircuitState 比较 Bug

**问题**：`CircuitBreaker.on_failure` 中 `*state != CircuitState::Open(Instant::now())` 永远为 true（两个不同时间的 Instant 不相等），导致每次失败都重置冷却计时器。

**修复**：

```rust
// 错误
if *state != CircuitState::Open(Instant::now()) { ... }

// 正确
if !matches!(*state, CircuitState::Open(_)) {
    *state = CircuitState::Open(Instant::now());
}
```

## 三、P1 — 编码初期应解决的设计问题

### 3.1 抽象 EventEmitter 解耦 Tauri

**问题**：agent-runtime 的 HumanGuard 直接持有 Tauri `AppHandle`，无法在 CLI、测试、Server 场景使用。

**建议**：引入 `EventEmitter` trait：

```rust
#[async_trait]
pub trait EventEmitter: Send + Sync {
    async fn emit(&self, event: &str, payload: impl Serialize + Send) -> Result<()>;
    async fn request_approval(&self, req: ApprovalRequest) -> Result<ApprovalResponse>;
}
```

Tauri 提供 `TauriEventEmitter`，测试用 `MockEventEmitter`，CLI 用 `TerminalEventEmitter`。

### 3.2 补全 AgentState 状态机

当前枚举缺少 `WaitingForApproval`、`WaitingForPlanConfirmation`、`Paused`、`StreamingLlmResponse`、`Cancelled`。建议合并 `GuardState` 到统一状态机，绘制完整状态转移图。

### 3.3 子 Agent 硬超时 + 清理机制

**问题**：子 Agent 只有心跳检测无硬超时，失控子 Agent 可能消耗大量 token。spawn 后 JoinHandle 无人消费，已完成的子 Agent 不从 children DashMap 中移除。

**建议**：
- 增加 `max_total_duration_secs`（默认 300s）硬超时
- `spawn` 持有 JoinHandle，完成后自动清理 children map
- 引入 `child_cancel_tokens`，父 Agent 取消时级联 cancel
- delegate_task 接口增加 `timeout_secs` 和 `max_iterations` 字段
- 结构化摘要增加 `token_usage: { input, output, total_cost_usd }`

### 3.4 子 Agent 强制屏蔽工具补充

当前 5 类屏蔽遗漏：
- `shell_bg`（后台进程）：子 Agent 启动的后台进程父 Agent 无法感知/清理
- `knowledge_manage`（知识库写入）：与 memory_write 同理，属跨会话持久副作用

### 3.5 HumanGuard check() 改用 watch channel

**问题**：当前 200ms 轮询 `RwLock<GuardState>` 是 async Rust 反模式。结构体中已有 `pause_rx` watch channel 但未使用。

**修复**：将 check() 中的轮询替换为 `self.pause_rx.changed().await`，实现零成本等待。

### 3.6 L2 审批超时从弹窗展示开始计时

**问题**：多个会话同时触发审批时，弹窗排队展示，但 30s 计时从后端发送时就开始了，用户可能还没看到弹窗就已超时被拒绝。

**建议**：前端展示弹窗时回调 `invoke("approval_displayed", { request_id })`，后端收到后才启动超时计时器。

### 3.7 TokenBudget 并发安全修复

**问题**：`record()` 的 `fetch_add` 后检查超限存在 TOCTOU 竞态：两个子 Agent 各消耗 50k，预算 80k，都通过检查但总消耗 100k。

**修复**：改用 `compare_exchange` 循环实现原子的"检查并扣减"。`children` 改为 `Arc<Mutex<Vec<...>>>` 或 DashMap。

### 3.8 非文本 Provider 支持多实例路由

**问题**：ProviderRegistry 中 `tts_client`、`image_client` 等为单个实例，无法运行时路由到不同 Provider。

**建议**：统一改为 `HashMap<String, Arc<dyn XxxClient>>`，与 `text_clients` 保持一致。key 使用 `provider/model` 格式。

### 3.9 白名单规则改用 JSONPath

**问题**：当前白名单用正则匹配序列化后的 JSON 字符串，JSON key 顺序不保证，不可靠。

**建议**：
- 改用 JSONPath 表达式匹配参数（如 `$.path starts_with "/tmp/"`)
- 增加 `mode: allow | deny` 支持黑名单
- 规则按顺序匹配，首条命中生效

### 3.10 MCP 工具风险等级可配置

**问题**：McpToolBridge 硬编码 `risk_level() = Medium`，只读 MCP 工具也需要 L2 弹窗。

**建议**：
- 在 `mcp-servers.toml` 中允许声明默认风险等级
- 支持按工具名覆盖：`risk_overrides = { "dangerous_tool" = "high" }`
- 名称含 `list/get/search/read` 的工具默认标记为 Low

## 四、P2 — v0.2 阶段改善

### 4.1 记忆系统简化

- **合并 L5 到 L3**：用户建模不是独立存储层，而是 L3 持久记忆的写入管道。简化为 4 层架构
- **Weibull 衰减延后**：v0.1 用 TTL 过期 + 手动删除；v0.2 用 LRU 淘汰；v0.3 引入 Weibull
- **MEMORY.md 容量提升到 3000 字符**（当前 2200 偏小）

### 4.2 RAG 分块策略分档

- **自动模式（默认）**：根据文档类型自动选策略（Markdown→ByParagraph+ParentChild、代码→tree-sitter、PDF→SlidingWindow）
- **专家模式**：设置中暴露全部 6 种策略
- 补充文档更新（re-ingest）逻辑
- 增加跨工作区"共享知识库"（`workspace_id = '__global__'`）

### 4.3 上下文压缩改善

- 统一压缩阈值（系统设计 80% vs 详细设计 75/85/95%，以详细设计的三级为准）
- 摘要 Prompt 增加结构化输出：关键决策 / 待完成任务 / 约束条件 / 背景信息
- 重要性评分扩展多语言支持（当前仅中文关键词）

### 4.4 Provider 抽象改善

- 提取 `AsyncTaskClient` trait 统一 Video/Music 的异步轮询模式
- 统一 TextClient 方法名为 `chat` / `chat_stream`
- `generate_lyrics` 从 MusicClient 移出，作为独立工具调用
- 流式中断改为"保留部分内容 + 完整重试"策略（而非拼接续写）

### 4.5 Skills 系统改善

- Draft 状态允许"试用模式"（手动调用带警告），降低创建门槛
- Evolving 期间仍使用当前版本，候选版本在 staging 独立验证
- Agent 自动合成 Skill 的成功率阈值从 3 次提高到 5 次不同输入
- BM25 Skill 检索补充嵌入向量作为二路召回

### 4.6 崩溃恢复设计

- 放弃"replay"概念，改为"resume"：加载完整 messages 历史，注入系统消息说明中断情况
- 每轮工具执行完成后写入 checkpoint（conversation_id + round_number）
- 启动时扫描 `status = 'running'` 的 conversations，标记为 interrupted 并提示用户

### 4.7 `<agent_plan>` 与 tool_calls 互斥

若 LLM 响应同时包含 `<agent_plan>` 和 tool_calls，应忽略 tool_calls，计划确认后由 LLM 下一轮重新生成。建议改用 `submit_plan` 工具调用替代 XML 解析。

## 五、设计亮点（值得保留）

以下设计决策经评审确认为优秀，不建议修改：

1. **冻结快照注入（MEMORY.md/USER.md）**：保证 Prompt Cache 100% hit rate + 行为一致性
2. **drain-on-release 接管释放机制**：精巧地解决了接管期间的状态一致性
3. **repair_dangling_tool_calls 崩溃恢复**：利用 messages 表做断点检测，避免复杂的 checkpoint
4. **网络重试分级策略**：429 退避 / 5xx 重试 / 4xx 不重试 / 3 次失败自动暂停
5. **RRF 混合检索**：BM25 + 向量的融合方法成熟可靠
6. **原子批量操作（operations[]）**：减少 LLM 调用轮次 + SQLite 事务保证一致性
7. **子 Agent 完全隔离架构**：无 context 污染、Token 高效、权限可收窄
8. **四级风险分级（L1-Critical）**：覆盖从只读到自我进化的完整风险谱
