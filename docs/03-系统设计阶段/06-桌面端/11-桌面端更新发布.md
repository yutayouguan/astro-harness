# Astro 桌面端打包与公开更新发布

Astro 的源码仓库保持私有（`yutayouguan/astro-agent`，私有）。安装包、更新签名和
`latest.json` 发布到独立的公开资产仓库（`yutayouguan/astro-agent-releases`），
客户端只访问该公开仓库。

> 前置状态检查：在 GitHub 上看到 0 个 workflow、0 个运行记录，或 latest-release
> 返回 404，都属于“还没发布过”，不是客户端 bug。私有仓库第一次推送包含
> `.github/workflows/**` 的提交后，Actions 页面可能需要手动点一次 Enable workflows。

## 1. 本机签名材料

### Tauri 更新签名（必需）

- 私钥：`~/.tauri/astro-agent.key`（0600，禁止提交）
- 密码：macOS 钥匙串服务 `com.astroagent.desktop.updater-signing`
- 公钥：`apps/desktop/src-tauri/updater.pub`（可公开，已纳入版本控制）

更新签名与系统代码签名是两件独立的事，不能互相替代：前者决定客户端能否校验更新包，
后者决定操作系统是否信任安装包。

轮换更新密钥：在 `apps/desktop` 下执行
`npx tauri signer generate --write-keys ~/.tauri/astro-agent.key`，用新生成的 `.pub`
替换仓库里的 `apps/desktop/src-tauri/updater.pub`。旧客户端无法验证新密钥签名的更新包，
因此要先发一个“内置新公钥、仍用旧私钥签名”的过渡版本。

### macOS 代码签名与公证（可选，当前未采购）

**当前状态：没有 Developer ID Application 证书，macOS 安装包按未签名发布。**
未签名的 `.dmg` 在别人机器上仍可安装，但首次打开会被 Gatekeeper 拦一次，用户需要
右键点 App 选「打开」，或执行
`xattr -dr com.apple.quarantine "/Applications/Astro Agent.app"`；这一步会写进
Release 说明，工作流也会在运行日志里给出 `::warning::`。

真要让用户双击即开，需要补下面这些材料（属于后续可选项）：

- Apple Developer Program 账号，创建 **Developer ID Application** 证书
- 从钥匙串导出 `.p12`，再转 base64 供 CI 使用
- 公证凭证：Apple ID + App 专用密码 + Team ID（或 App Store Connect API Key）

### Windows 代码签名（可选，当前未采购）

**当前状态：没有代码签名证书，Windows 安装包按未签名发布**，SmartScreen 会提示
“未知发布者”，用户点「更多信息 → 仍要运行」即可。补齐下面材料后可消除该提示：

- 从 CA 购买 OV/EV 代码签名证书，导出 `.pfx`
- 转 base64 供 CI 使用；工作流会把证书导入 runner 的
  `Cert:\CurrentUser\My`，再用指纹让 signtool 签名

## 2. GitHub Secrets

全部配置在私有源码仓库（不是资产仓库）：

```bash
gh auth login

# 1) 公开资产仓库 token：fine-grained PAT，仅对 astro-agent-releases 有 Contents: Read and write
gh secret set ASTRO_RELEASE_TOKEN

# 2) Tauri 更新签名
gh secret set TAURI_SIGNING_PRIVATE_KEY < ~/.tauri/astro-agent.key
security find-generic-password \
  -a "$USER" \
  -s com.astroagent.desktop.updater-signing \
  -w | gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD

# 3) macOS 代码签名与公证（可选，当前没有证书，先跳过）
base64 -i Certificates.p12 -o apple-cert-base64.txt
gh secret set APPLE_CERTIFICATE < apple-cert-base64.txt
gh secret set APPLE_CERTIFICATE_PASSWORD
gh secret set APPLE_ID
gh secret set APPLE_PASSWORD                 # App 专用密码，不是 Apple ID 登录密码
gh secret set APPLE_TEAM_ID
# 可选：证书里有多个 Developer ID 时才需要
gh secret set APPLE_SIGNING_IDENTITY

# 4) Windows 代码签名（可选，当前没有证书，先跳过）
base64 -i CodeSign.pfx -o win-cert-base64.txt
gh secret set WINDOWS_CERTIFICATE < win-cert-base64.txt
gh secret set WINDOWS_CERTIFICATE_PASSWORD
```

配置完请删除本地的 `*-base64.txt`。私钥、证书和密码都不得进入仓库、Release 资产或日志。

`release-tauri` 的前置检查会逐个核对上面这些 secret：

- 必需的三个（资产仓库 token、更新私钥、更新私钥密码）缺失时直接失败；
- macOS / Windows 的代码签名密钥缺失时**不阻塞发布**，只在日志里给出 `::warning::`、
  在运行摘要里标注每个平台的签名状态，并把安装提示写进 Release 说明；
- 拿到证书后，手动运行工作流并勾选 `require_signing`，即可让缺证书直接失败。

## 3. 版本号

版本号在四处保持一致：`apps/desktop/src-tauri/tauri.conf.json`、
`apps/desktop/package.json`、`apps/desktop/src-tauri/Cargo.toml`、`Cargo.lock`。

```bash
node tools/bump-version.mjs 0.2.0     # 写入新版本号并同步 Cargo.lock
node tools/bump-version.mjs --check   # 只校验一致性（CI 会跑）
```

`quality` 工作流和 `release-tauri` 的前置检查都会执行 `--check`；推送 tag 时还会额外
校验 `v<版本号>` 与 `tauri.conf.json` 完全一致。

## 4. 发布

```bash
# 1) 先验证三平台能编译（不需要任何签名密钥）
gh workflow run build-tauri.yml

# 2) 更新版本号与 RELEASE_NOTES.md，提交
node tools/bump-version.mjs 0.2.0
$EDITOR RELEASE_NOTES.md
git commit -am "chore(release): v0.2.0"

# 3) 打 tag 并推送，触发发布
git tag v0.2.0
git push origin HEAD --tags        # 需要用户明确授权后再执行
```

也可以手动触发：`gh workflow run release-tauri.yml`（缺系统代码签名时出未签名包）。
证书到位后加 `-f require_signing=true`，缺证书就会直接失败。

发布工作流会：

1. 在私有源码仓库的 runner 上构建三平台安装包；
2. 有证书时 macOS 走 Developer ID 签名 + 公证 + stapler、Windows 走 signtool 签名；
   没证书时照常出包，并在日志、运行摘要和 Release 说明里标注未签名；
3. 用 Tauri 私钥签名更新包，上传安装包、`.sig` 和 `latest.json` 到公开资产仓库；
4. 创建公开且非草稿的 Release（tag 含 `-beta` / `-nightly` 时标记为 prerelease）；
5. `verify-release` 作业下载该 Release 的 `latest.json`，确认版本一致且
   `darwin-aarch64`、`darwin-x86_64`、`windows-x86_64`、`linux-x86_64`
   四个平台条目齐全。缺任何一个就判定发布失败——矩阵作业是并行上传同一个
   `latest.json` 的，这一步是防止出现“部分平台收不到更新”。

构建时客户端会写入更新地址：

```text
https://github.com/yutayouguan/astro-agent-releases/releases/latest/download/latest.json
```

本地开发构建未设置 `ASTRO_UPDATE_ENDPOINT` 时，关于页会明确显示更新功能尚未配置。

## 5. 发布后验收

CI 只能证明“清单齐全、签名步骤按配置执行”，不能替代真机验收：

1. macOS 上打开 DMG 安装：
   - 已有 Developer ID 时，应无“无法验证开发者”提示，且
     `codesign --verify --deep --strict`、`xcrun stapler validate`、`spctl -a -vv` 均通过；
   - 当前未签名时，验证 Release 说明里的安装提示确实可用：右键「打开」能启动，
     `xattr -dr com.apple.quarantine` 之后可以正常双击启动。
2. Windows 上安装 MSI/NSIS 包：有证书时发布者应显示为证书主体；未签名时确认
   “更多信息 → 仍要运行”能装成功且应用可用。
3. Linux 上安装 AppImage / deb：确认 desktop 入口、图标、托盘可用。
4. 用一个旧版本安装包升级到新版本，验证应用内检查更新、下载、重启后版本号变化。
5. 旧版本迁移：旧 JSON / 旧目录必须先走显式离线迁移，不能用覆盖安装或自动更新冒充迁移。

历史验收记录见 [`docs/release-acceptance.md`](../../release-acceptance.md)。

## 6. 已知边界

- **macOS / Windows 当前未做系统代码签名**：没有 Developer ID Application 证书和
  Windows 代码签名证书，安装包按未签名发布，首启分别会出现 Gatekeeper 拦一次、
  SmartScreen “未知发布者”。补齐证书后在 `release-tauri` 里勾选 `require_signing`
  即可恢复强制校验。
- Linux 包在 `ubuntu-22.04` 上构建，要求 glibc 2.35 及以上的发行版。
- 目前只出 macOS arm64/x64、Windows x64、Linux x64；没有 macOS universal、
  Windows ARM64 与 Linux ARM64。
- Windows 安装包使用 `embedBootstrapper`，安装时仍需联网下载 WebView2；
  完全离线安装需要改为 `offlineInstaller`（安装包会增大到约 130MB）。
- **Windows 暂时只出 NSIS `setup.exe`**：WiX/MSI 在当前工程上 `light.exe` 打包失败
  （错误信息未回显，需要单独排查），而应用内更新的 Windows 产物本来就优先用 NSIS；
  工作流通过 `--bundles nsis` 显式收窄，不在打包阶段阻塞发布。
- `evolution-dspy` 的 Python 源码通过 `bundle.resources` 随包分发，属于可被解开的
  分发内容；对外口径需要与闭源许可保持一致。
