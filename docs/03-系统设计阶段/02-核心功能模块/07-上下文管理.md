# 上下文管理与 Token 优化

> **Harness 基线（2026-09-07）**：当前上下文由 `PromptContract`、角色化 dynamic context、独立 tool schemas 和 provider history 组成。工具结果按 `maintain_tool_context()` 三阶段维护（prune → LLM compaction → head/tail fallback），`content` 保留原文，`compressed_content` 仅作 Provider 视图。工具深度由双重预算并行控制：`TurnState.tool_rounds`（per-turn）和 `IterationBudget`（per-thread）。大工具结果通过 Tool Spill 落盘。

> 阶段：系统设计 | 状态：定稿 | 说明：上下文压缩、工具深度预算、Tool Spill

## 概述

大型语言模型的上下文窗口是有限的资源。当对话轮次增多、工具调用结果不断追加时，上下文很快会触及上限。本文档描述 Astro Agent 的核心上下文管理机制：**工具结果压缩（`maintain_tool_context`）**、**工具深度预算（双重机制）**、**Tool Spill**，确保长对话仍能高效运行。

## 1. 上下文压缩（`maintain_tool_context()` 三阶段）

> **架构决策**：`maintain_tool_context()` 采用三阶段级联策略，对工具结果进行渐进式压缩。`content` 字段永远保留原文，`compressed_content` 字段仅存 Provider 视图。

三阶段流程：

```text
maintain_tool_context()
  ├── 阶段 1: Prune（截断超大 tool 结果）
  │   └── 尾部保护区外、超过 PRUNE_MIN_CHARS (200) 的 tool 结果可廉价清除
  ├── 阶段 2: LLM 辅模型摘要（AuxiliaryTask::Compaction）
  │   └── 使用辅助模型生成压缩摘要，写入 compressed_content
  └── 阶段 3: Head/tail fallback
      └── 摘要失败时，保留头尾内容作为最后手段
```

关键不变量：
- `content` 字段永远保留原文（原生历史完整性）
- `compressed_content` 字段存 Provider 视图（模型看到的是压缩后版本）
- 压缩前后触发 `PreCompact` / `PostCompact` hook 事件
- thrashing guard 防止频繁压缩

### Tool Spill

工具结果 >= `DEFAULT_SPILL_THRESHOLD_BYTES`（16 KB）时自动落盘，provider history 使用 stub 替代：

```text
tool 结果 >= 16 KB
  -> 原始内容写入磁盘文件
  -> provider history 中替换为 stub（含路径引用）
  -> canonical 历史保持完整 ResponseItem
```

## 2. 工具深度预算（双重机制）

当前架构使用两套独立预算并行生效，任一耗尽均终止当前 turn：

### 机制一：`TurnState.tool_rounds`（per-turn）

每条用户消息归零，上限 `config.multi_turn`（默认 `DEFAULT_MAX_ITERATIONS` = 90）。`increment_tool_round()` 耗尽时返回 `MaxDepthError`。

### 机制二：`IterationBudget`（per-thread）

每个 Agent Thread 独立预算（默认 90），`code_exec` 类型轮次可通过 `refund()` 退还，允许更多非计算轮次。

```rust
// crates/agent-core/src/runtime/budget.rs

pub const DEFAULT_MAX_ITERATIONS: usize = 90;

pub struct IterationBudget {
    max_total: usize,
    used: Cell<usize>,
}

impl IterationBudget {
    pub fn new(max_total: usize) -> Self { ... }
    pub fn consume(&self) -> Result<(), MaxDepthError> { ... }
    pub fn refund(&self) { ... }  // code_exec 可退还
}
```

### Streaming 不变量

每轮 assistant 回复先写入再执行工具；usage 覆盖式累加（兼容 Google 累计式 usageMetadata）。

## 3. 原生历史与消息顺序

当前架构使用 `ResponseItem` 作为原生历史格式。Agent、rollout、SQLite 和 Desktop history RPC 都使用 `ResponseItem`。

### 消息顺序不变量

相邻的 user/assistant message item 不得重复角色，由 `validate_message_order()` 强制。

### Prompt 组装

`PromptContract` 组装上下文时，工具 schemas 独立于历史传递，压缩后的 `compressed_content` 仅影响 Provider 视图，不影响 canonical 历史中的原始 `content`。

## 4. Pending 消息队列

### 队列目标

Agent 运行期间，用户可能追加新消息（补充需求、中途修改指令）。这些消息不应打断当前执行轮次，而是入队等待，在本轮完成后注入下一轮 context。

> **持久化决策**：Pending 消息仅保存在内存，不写入数据库。Agent 崩溃时队列丢失，用户需重新输入。此决策基于实现简洁性——崩溃概率低，且用户能通过界面感知 Agent 异常终止。

### PendingQueue 实现

```rust
// crates/agent-runtime/src/pending_queue.rs

use std::sync::Arc;
use tokio::sync::Mutex;

pub struct PendingQueue {
    messages: Arc<Mutex<Vec<PendingMessage>>>,
}

#[derive(Debug, Clone)]
pub struct PendingMessage {
    pub content: String,
    pub attachments: Vec<Attachment>,
    pub enqueued_at: chrono::DateTime<chrono::Utc>,
}

impl PendingQueue {
    pub fn new() -> Self {
        Self { messages: Arc::new(Mutex::new(vec![])) }
    }

    /// 前端追加消息时调用（Agent 运行中）
    pub async fn push(&self, msg: PendingMessage) {
        self.messages.lock().await.push(msg);
    }

    /// 轮次开始时取出所有 pending 消息并清空队列
    pub async fn drain(&self) -> Vec<PendingMessage> {
        std::mem::take(&mut *self.messages.lock().await)
    }
}
```

### AgentRuntime 集成点

```rust
// crates/agent-runtime/src/runtime.rs

impl AgentRuntime {
    pub async fn round_loop(&self) -> Result<()> {
        loop {
            // ① 注入 pending 消息（上一轮结束后用户追加的消息）
            for msg in self.pending_queue.drain().await {
                self.context.add(Message::user(
                    vec![ContentPart::Text { text: msg.content }],
                    ContextSlot::Regular,
                ));
            }

            // ② LLM 调用（含自适应规划指令注入 System Prompt）
            let response = self.llm_call().await?;

            // ③ 工具执行（经 HumanGuard，含 L1/L2/L3 + YOLO 判断）
            self.execute_tools(&response).await?;

            // ④ 无更多工具调用 → 退出，等待下一轮用户输入
            if !response.has_tool_calls() {
                break;
            }
        }
        Ok(())
    }
}
```

### Tauri Command

```rust
// src-tauri/src/commands/agent.rs

/// 用户在 Agent 运行期间追加消息
#[tauri::command]
pub async fn append_pending_message(
    conversation_id: String,
    content: String,
    state: State<'_, AppState>,
) -> Result<(), String> {
    let runtime = state.get_runtime(&conversation_id)
        .ok_or("Agent 未运行")?;
    runtime.pending_queue.push(PendingMessage {
        content,
        attachments: vec![],
        enqueued_at: chrono::Utc::now(),
    }).await;
    Ok(())
}
```

## 5. 配置示例

```toml
# config/context.toml

[context]
# 三级级联压缩阈值（自动升级，无需手动选择策略）
light_threshold = 0.75       # 75%: 轻量压缩（滑动窗口 + 低分消息移除）
summary_threshold = 0.85     # 85%: 摘要压缩（LLM 生成历史摘要）
emergency_threshold = 0.95   # 95%: 紧急压缩（仅保留最近 N 条 + pinned + tool pairs）

[context.light]
keep_recent = 10             # 轻量压缩时强制保留最近 N 条消息

[context.summary]
keep_recent = 20             # 摘要压缩时强制保留最近 N 条消息
model = "claude-haiku-4-5"   # 用于生成摘要的模型（选择便宜的快速模型）
max_summary_tokens = 500

[token_budget]
# 各槽位占上下文窗口的比例（按模型 context window 自动计算）
system_prompt_ratio = 0.15
tool_definitions_ratio = 0.10
memory_snapshot_ratio = 0.10
knowledge_context_ratio = 0.10
# 剩余 55% 留给对话历史
```
