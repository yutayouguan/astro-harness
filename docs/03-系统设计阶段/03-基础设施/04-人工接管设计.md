> **Harness 基线（2026-09-07）**：当前控制面由 interaction mode、`HitlGate`、`PauseControl`、`SessionApprovalCache`（会话级审批缓存，同命令模式不重复弹窗）、`SmartApprovalContext`（对话上下文感知审批）、工具/MCP 审批与 `Op/EventMsg` 共同组成。旧 `HumanGuard` 三级状态机伪代码不是当前实现契约。

## 1. 设计目标

### 1.1 三种接管模式

> **注意**：本节使用描述性名称而非 L1/L2/L3 编号，避免与工具风险等级（见 2.1 节）混淆。

| 接管模式 | 触发场景 | 含义 |
| -------- | -------- | ---- |
| **单次审批** | L2/L3 风险工具触发 HumanGuard | Agent 暂停当前操作，等待用户对单个工具调用批准或拒绝，决定后自动恢复 |
| **任务暂停** | 用户发 `/pause`、极高风险操作（进化/自修改）、网络连续失败 | Agent 完成当前原子操作后挂起整个任务，等待用户手动恢复 |
| **完全接管** | 用户按 `Ctrl+Shift+S` 紧急停止 | 用户获得对工具调用的直接控制权，Agent 退出自主决策循环 |

### 1.2 设计原则

- **最小中断**：仅在必要时打断 Agent，低风险操作通过白名单静默放行
- **明确边界**：每次中断必须清晰展示"Agent 想做什么、为什么有风险、用户能做什么"
- **可审计**：所有审批决定写入不可篡改的审计日志，保留完整上下文

---

## 1.3 计划确认与接管的区别

自适应规划（F-39）触发的 `plan_confirmation_required` 事件**不属于接管机制**，两者在触发点和目的上正交：

| 维度 | 计划确认（`plan_confirmation_required`） | HumanGuard 接管（本文档） |
| ---- | --------------------------------------- | ------------------------- |
| **触发点** | LLM 输出 `<agent_plan>` 块（LLM 调用之后、工具执行之前） | 每个工具调用进入 `ToolRegistry.execute_checked()` 时 |
| **目的** | 让用户看到并确认/修改整体执行计划 | 对单个高风险工具调用进行审批 |
| **粒度** | 整轮任务级别 | 单次工具调用级别 |
| **状态影响** | 用户取消 → 终止本轮；确认 → 进入工具执行阶段 | Rejected → 跳过该工具调用，Agent 继续 |
| **受 YOLO 影响** | **否**（YOLO 不跳过计划确认） | **是**（YOLO ON 时 L2/L3 直接放行） |

## 2. 触发机制

### 2.1 触发条件分级表

工具风险分为 L1/L2/L3 三级（与 PRD F-38 对齐），极高风险单独处理：

| 风险等级 | 默认行为 | 典型场景 |
| -------- | -------- | -------- |
| **L1**（低） | 白名单静默放行，无弹窗 | 读取文件、查询网页、调用只读 API |
| **L2**（中） | **单次审批**弹窗，30s 超时自动拒绝 | 写入工作区文件、调用外部服务写接口 |
| **L3**（高） | **单次审批**弹窗，无超时，必须手动决定 | 删除文件、网络写操作、生成子 Agent |
| **极高** | 强制**任务暂停**，需二次确认后恢复 | 进化/自修改操作（`EvolutionAction`）、批量删除 |

> 超时默认行为选择拒绝而非批准：用户未响应说明可能未看到弹窗，自动批准写操作存在安全风险；拒绝后 Agent 记录该步骤已跳过并继续执行，用户可在下一轮手动补充。

### 2.2 自动触发 vs 用户主动触发

**自动触发**：`HumanGuard` 在 `GuardTrigger` 命中时自动拦截，映射如下：

- `ToolCall` → 中风险（视工具白名单决定是否放行）
- `WriteFile` → 中风险
- `NetworkWrite` → 高风险
- `SpawnAgent` → 高风险
- `EvolutionAction` → 极高风险

**用户主动触发**：

- 在对话框输入 `/pause` → 触发 L2 暂停
- 快捷键 `Ctrl+Shift+S`（紧急停止）→ 立即触发 L3 完全接管，Agent 停止所有待执行操作

### 2.3 白名单机制

在 `workspace.yaml` 中配置 `human_guard.whitelist`，命中的工具调用跳过审批直接执行。

```rust
pub struct WhitelistRule {
    pub tool_name: String,
    pub mode: WhitelistMode,           // Allow or Deny
    pub args_match: Option<ArgsMatch>, // JSONPath 替代正则
}

pub enum WhitelistMode {
    Allow,  // 匹配则免审批
    Deny,   // 匹配则强制审批（黑名单）
}

pub enum ArgsMatch {
    /// JSONPath 表达式匹配，如 $.path starts_with "/tmp/"
    JsonPath { path: String, operator: String, value: String },
    /// 简单值匹配（向后兼容）
    Equals { field: String, value: String },
}
```

> 规则按顺序匹配，首条命中生效（类似防火墙规则）。JSONPath 替代正则匹配 JSON 字符串，避免 JSON key 顺序不确定导致的匹配失败。

## 3. 状态机设计

```text
                  ┌─────────────────────────────────────────┐
                  │                                         │
  [启动]          ▼         [触发审批]                      │
  ──────► RUNNING ──────────────────► PENDING_APPROVAL      │
             ▲                          │          │         │
             │            [批准]        │          │[拒绝]   │
             │◄─────────── APPROVED ◄──┘          │         │
             │                                    ▼         │
             │                              REJECTED        │
             │                          (操作取消，继续)    │
             │                                    │         │
             │◄───────────────────────────────────┘         │
             │                                              │
             │  [/pause 或超时]                             │
             ├──────────────────────► PAUSED               │
             │                          │                   │
             │              [resume]    │  [takeover]       │
             │◄─────────────────────────┤                   │
             │                          ▼                   │
             │                      TAKEOVER ──[release]───┘
             │                          │
             └──────────────────────────┘
                       [release]
```

| 状态 | 定义 | 允许转换 |
| ---- | ---- | -------- |
| `RUNNING` | Agent 自主执行中 | → PENDING_APPROVAL, → PAUSED, → TAKEOVER |
| `PENDING_APPROVAL` | 等待用户对单个操作决策 | → APPROVED, → REJECTED |
| `APPROVED` | 操作被批准，准备恢复 | → RUNNING |
| `REJECTED` | 操作被拒绝，跳过该步骤 | → RUNNING |
| `PAUSED` | Agent 挂起，不执行任何操作 | → RUNNING (resume), → TAKEOVER |
| `TAKEOVER` | 用户完全控制工具调用 | → RUNNING (release) |

## 4. Rust 实现设计

### 4.1 HumanGuard 数据结构

> 实现位于 `crates/agent-runtime/src/guard/human_guard.rs`（通过 `EventEmitter` trait 抽象环境依赖，不直接依赖 Tauri）。

```rust
pub struct HumanGuard {
    state: Arc<RwLock<GuardState>>,
    config: HumanGuardConfig,
    whitelist: Whitelist,
    /// per-request oneshot：key = request_id，value = 审批结果 Sender
    /// 支持并发多个工具调用同时等待审批（MultiTask 场景）
    pending_decisions: DashMap<Uuid, oneshot::Sender<ApprovalResponse>>,
    /// 环境解耦的事件发射器，支持 Tauri / CLI / 测试等不同运行环境
    /// （详细设计阶段将 AppHandle 抽象为 trait，避免 agent-runtime 直接依赖 Tauri）
    emitter: Arc<dyn EventEmitter>,
    /// SQLite 连接池，写入 audit_logs 表
    pool: SqlitePool,
    /// Guard 状态广播；LLM 调用和工具执行通过 select! 即时感知
    state_tx: watch::Sender<GuardState>,
    pub state_rx: watch::Receiver<GuardState>,
}

impl HumanGuard {
    /// 工具调用唯一入口：L1 直通，L2 弹窗(30s 超时自动拒绝)，L3 弹窗(无超时)
    pub async fn check(&self, tool: &dyn Tool, input: &ToolInput)
        -> Result<ApprovalOutcome, GuardError>;

    /// 切换暂停状态（/pause 命令 或 极高风险触发），广播 pause_tx
    pub fn set_paused(&self, paused: bool);

    /// 进入完全接管模式（Ctrl+Shift+S）
    pub async fn takeover(&self) -> Result<(), GuardError>;

    /// 释放接管，Agent 恢复自主运行
    pub async fn release(&self) -> Result<(), GuardError>;

    /// 前端审批回调（approve_action / reject_action Tauri Command 调用）
    pub fn resolve(&self, request_id: Uuid, response: ApprovalResponse);
}
```

### 4.2 核心数据结构

```rust

    pub decided_at: DateTime<Utc>,

```

### 4.3 超时策略

| 风险等级 | 超时时长 | 超时默认行为 |
| -------- | -------- | ------------ |
| L1 | 无弹窗 | 自动执行 |
| L2 | 30s | `Rejected`（跳过该工具调用，Agent 继续） |
| L3 | 无超时 | 必须手动决定 |
| 极高 | 无超时 | 进入任务暂停，等待恢复指令 |

超时由 `HumanGuard::check` 内部 `tokio::time::timeout(Duration::from_secs(config.timeout_secs))` 实现，超时即向对应 `oneshot::Sender` 注入 `ApprovalOutcome::Rejected` 结果并触发 `tool_rejected` 审计日志。

> **审批超时计时起点**：L2 的 30s 超时从弹窗**展示给用户的那一刻**开始计算，而非从后端发送 `ApprovalRequest` 的时刻。实现方式：后端发送审批请求后暂不启动计时器；前端展示弹窗时回调 `invoke("approval_displayed", { request_id })`；后端收到回调后才启动 `tokio::time::timeout(30s, rx.recv())`。这避免了多会话并发审批时弹窗排队导致的"未看到就超时"问题。

### 4.4 与 agent-runtime 的集成点

`AgentRuntime` 在执行每个工具调用前调用 `human_guard.check()`，返回 `Rejected` 则跳过并记录原因；返回 `ModifiedAndApproved` 则以修改后的参数执行。`PAUSED` 和 `TAKEOVER` 状态下 `check()` 通过 watch channel 零成本等待：

```rust
impl HumanGuard {
    pub async fn check(&self, tool: &dyn Tool, input: &ToolInput)
        -> Result<ApprovalOutcome, GuardError>
    {
        // 使用 watch channel 零成本等待，替代 200ms 轮询（async Rust 最佳实践）
        while *self.pause_rx.borrow() {
            self.pause_rx.changed().await.ok();
        }

        let risk = self.whitelist.evaluate(tool, input);
        match risk {
            RiskLevel::Low => Ok(ApprovalOutcome::Approved),      // L1 白名单直通
            RiskLevel::Medium => self.request_approval(tool, input, Some(30)).await,  // L2 30s 超时
            RiskLevel::High => self.request_approval(tool, input, None).await,        // L3 无超时
            RiskLevel::Critical => {
                self.set_paused(true);                             // 极高 → 任务暂停
                Err(GuardError::ForcePaused)
            }
        }
    }
}
```

> **为什么用 watch channel 而非轮询？** 原始设计使用 `loop { match *self.state.read().await { GuardState::Paused => sleep(200ms) } }` 轮询模式，在暂停期间每秒唤醒 5 次做无意义检查。`watch::Receiver::changed()` 是零成本等待——仅在 `pause_tx.send()` 实际发送时才唤醒，CPU 占用从 O(1/200ms) 降至 O(0)，且响应延迟从最差 200ms 降至微秒级。

### 4.5 并行工具调用的批量审批

当 LLM 一轮返回多个需要审批的 tool_calls 时，采用批量审批模式避免弹出多个独立弹窗：

**触发条件**：同一轮 `tool_calls` 中有 2 个及以上 L2/L3 级别的工具调用。

**审批 UI**：

```text
┌─────────────────────────────────────────┐
│  ⚠️ Agent 请求执行以下 3 个操作          │
├─────────────────────────────────────────┤
│  ☐ file_write("/src/main.rs", ...)  [M] │
│  ☐ shell_exec("cargo build")       [H] │
│  ☐ http_request("https://...")      [M] │
├─────────────────────────────────────────┤
│  [全部批准] [全部拒绝] [逐项选择]        │
└─────────────────────────────────────────┘
```

**行为规则**：

1. **全部批准**：所有工具调用并发执行（`tokio::join_all`）
2. **全部拒绝**：所有工具调用注入 `UserRejected` 错误到上下文
3. **逐项选择**：用户勾选要执行的工具，未勾选的注入拒绝。被批准的工具并发执行
4. **超时**：批量审批的超时按最高风险级别决定（含 L3 则无超时，仅 L2 则 30s）
5. **L1 工具不出现在批量弹窗中**：自动执行，不阻塞其他工具的审批流程

**实现**：

```rust
pub struct BatchApprovalRequest {
    pub batch_id: Uuid,
    pub items: Vec<ApprovalItem>,
    pub timeout: Option<Duration>,  // None = 无超时（含 L3 工具时）
}

pub struct ApprovalItem {
    pub call_id: String,
    pub tool_name: String,
    pub risk_level: RiskLevel,
    pub args_preview: String,      // 参数摘要（截断到 200 字符）
}

pub struct BatchApprovalResponse {
    pub batch_id: Uuid,
    pub decisions: HashMap<String, ApprovalOutcome>,  // call_id → 决定
}
```

## 8. 配置规范

### 8.1 workspace.yaml 示例

```yaml
human_guard:
  enabled: true
  l2_timeout_secs: 30               # L2 弹窗超时（L3 无超时，必须手动决定）
  default_on_timeout: rejected      # 固定 rejected，不可改为 approved（安全原则）

  risk_thresholds:
    auto_approve_below: low         # 低于此级别静默放行
    force_pause_above: high         # 高于此级别强制 L2 暂停

  whitelist:
    - tool_name: "read_file"
      mode: allow
    - tool_name: "web_search"
      mode: allow
    - tool_name: "write_file"
      mode: allow
      args_match:
        type: json_path
        path: "$.path"
        operator: "starts_with"
        value: "/tmp/astro-agent/"         # 仅允许写入临时目录
    - tool_name: "delete_file"
      mode: deny                           # 黑名单：强制审批

  audit:
    enabled: true
    log_path: "~/.astro/audit.jsonl"
    retention_days: 90

  shortcuts:
    emergency_stop: "Ctrl+Shift+S"
```

### 8.2 配置项说明

| 配置项 | 说明 |
| ------ | ---- |
| `enabled` | 总开关，关闭后所有操作直接放行（仅限开发环境） |
| `timeout_secs` | 审批弹窗超时时间，超时后按 `default_on_timeout` 处理 |
| `default_on_timeout` | 超时默认行为；所有风险级别超时均固定为 `rejected`（安全原则：用户未响应说明可能未看到弹窗，自动批准存在安全风险） |
| `risk_thresholds.auto_approve_below` | 低于该等级的操作匹配白名单后跳过审批 |
| `risk_thresholds.force_pause_above` | 高于该等级强制进入 L2 暂停而非 L1 审批 |
| `whitelist[].mode` | `allow`（免审批）或 `deny`（强制审批），规则按顺序匹配，首条命中生效 |
| `whitelist[].args_match` | JSONPath 表达式匹配工具参数（替代正则，避免 JSON key 顺序不确定导致匹配失败） |
| `audit.retention_days` | 审计日志保留天数，超期自动清理 |
| `shortcuts.emergency_stop` | 紧急停止快捷键，触发 L3 完全接管 |
