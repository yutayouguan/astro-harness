## 二、FTS5 全文索引设计

### 2.1 memory_entries 全文检索

记忆条目字段为 `key`（键名）+ `value`（内容），使用 FTS5 + unicode61 分词器支持中英文混合搜索：

```sql
-- migrations/004_fts.sql

CREATE VIRTUAL TABLE memory_entries_fts USING fts5(
    key,
    value,
    content='memory_entries',
    content_rowid='rowid',
    tokenize='unicode61 remove_diacritics 1'
);

-- 触发器保持 FTS 与原表同步（仅索引活跃版本）
CREATE TRIGGER memory_fts_ai AFTER INSERT ON memory_entries
    WHEN new.valid_to IS NULL
BEGIN
    INSERT INTO memory_entries_fts(rowid, key, value)
    VALUES (new.rowid, new.key, new.value);
END;

-- 更新触发器：先删除旧记录，条件插入新记录
CREATE TRIGGER memory_fts_au AFTER UPDATE ON memory_entries BEGIN
    -- 旧版本从 FTS 移除
    INSERT INTO memory_entries_fts(memory_entries_fts, rowid, key, value)
    VALUES ('delete', old.rowid, old.key, old.value);
    -- 若新版本仍活跃则重新插入（WHERE 子句实现条件插入，替代无效的 CASE 表达式）
    INSERT INTO memory_entries_fts(rowid, key, value)
    SELECT new.rowid, new.key, new.value
    WHERE new.valid_to IS NULL;
END;
```

查询示例：

```sql
-- BM25 全文检索，结合工作区过滤，只看活跃版本
SELECT e.id, e.key, e.value, bm25(memory_entries_fts) AS rank
FROM memory_entries_fts
JOIN memory_entries e ON e.rowid = memory_entries_fts.rowid
WHERE memory_entries_fts MATCH ?
  AND e.workspace_id = ?
  AND e.valid_to IS NULL
ORDER BY rank
LIMIT 20;
```

### 2.2 skills BM25 全文检索

技能搜索需要按 name + content 联合召回（POC-06 已验证 BM25 准确率 >90%）：

```sql
CREATE VIRTUAL TABLE skills_fts USING fts5(
    name,
    content,
    content='skills',
    content_rowid='rowid',
    tokenize='unicode61'
);

-- 查询：仅检索 active 版本，按 BM25 排序
SELECT s.id, s.name, s.version, bm25(skills_fts) AS rank
FROM skills_fts
JOIN skills s ON s.rowid = skills_fts.rowid
WHERE skills_fts MATCH ?
  AND s.status = 'active'
ORDER BY rank
LIMIT 5;
```

### 2.3 FTS5 中文分词支持

SQLite FTS5 默认按空格分词，对中文支持极差。项目采用以下方案：

**方案：自定义 tokenizer + jieba-rs**

通过 SQLite FTS5 的自定义 tokenizer API 注册 jieba 分词器：

- 依赖 `jieba-rs` crate（纯 Rust 实现，无外部依赖）
- 应用启动时通过 `fts5_api_from_db()` 注册自定义 tokenizer `jieba`
- FTS5 虚拟表创建时指定 tokenizer：

```sql
CREATE VIRTUAL TABLE messages_fts USING fts5(
    content,
    tokenize='jieba'
);
```

**降级方案**：

如果 jieba-rs 注册失败（如 SQLite 版本过低），降级使用 `unicode61` tokenizer（按 Unicode 字符边界分词，精度低但不依赖外部库）。

**性能预期**：

| 操作 | jieba tokenizer | unicode61 (降级) |
| ---- | ---- | ---- |
| 索引写入 | ~2ms/条 | ~0.5ms/条 |
| 搜索 Top-20 | < 30ms | < 10ms |
| 中文查全率 | > 90% | ~40% |

## 三、复合索引设计

多维过滤是本项目最高频的查询模式（工作区隔离 + 时间范围），复合索引列顺序遵循"等值列在前，范围列在后"原则：

```sql
-- 工作区 + 时间范围：对话历史查询
-- 注：此索引未在 01-Schema设计.md 中声明，Schema 中对话表使用 idx_conv_pinned 索引；
-- 若需按时间范围查询对话列表，应在迁移文件中补充此索引定义。
CREATE INDEX idx_conversations_ws_time
    ON conversations(workspace_id, created_at DESC);

-- 工作区 + 时间范围：成本聚合（GROUP BY model）
CREATE INDEX idx_cost_ws_date
    ON cost_records(workspace_id, recorded_at DESC);

-- 工作区 + 操作类型：进化日志查询
CREATE INDEX idx_evolog_ws
    ON evolution_log(workspace_id, created_at DESC);

-- 记忆 Weibull 衰减扫描（仅活跃版本，遗忘调度器使用）
CREATE INDEX idx_memory_weibull
    ON memory_entries(workspace_id, category, retrieval_count, created_at)
    WHERE valid_to IS NULL;

-- 记忆活跃版本唯一约束（partial unique index）
CREATE UNIQUE INDEX idx_memory_active_key
    ON memory_entries(workspace_id, category, key)
    WHERE valid_to IS NULL;

-- 媒体任务状态轮询（TaskPoller 使用）
CREATE INDEX idx_media_tasks_status
    ON media_tasks(status)
    WHERE status IN ('pending', 'processing');
```

## 四、索引选择原则

**建索引的条件：**
- 字段出现在 WHERE、JOIN ON、ORDER BY 子句中，且过滤性（selectivity）足够高（重复值少于总行数 20%）
- 查询频率高、表行数超过 1 万行
- 复合查询中有固定的等值 + 范围模式（如 workspace_id + created_at）

**不建索引的情况：**
- 布尔型或枚举值极少（如 role 只有 user/assistant/tool，不值得单独索引）
- 写多读少的中间日志表（频繁写入时索引维护成本超过查询收益）
- JSON 字段内部路径（steps、metrics、payload）：改用 SQLite 的 JSON 提取函数做运行时过滤，或在应用层反序列化后处理
- FTS5 虚拟表本身已内置倒排索引，不需要在原表相同字段重复建 B-tree 索引

## 五、查询性能目标

| 查询类型 | 目标响应时间 | 说明 |
| --- | --- | --- |
| 按工作区 + 时间范围拉取对话列表 | < 10ms | 命中复合索引，结果集 ≤ 100 行 |
| 按 conversation_id 拉取全部消息 | < 5ms | 单索引点查 |
| FTS5 记忆条目全文搜索（BM25 Top-20） | < 30ms | 含工作区 JOIN 过滤，仅活跃版本 |
| 记忆 KNN 检索（Top-8，sqlite-vec） | < 100ms | 自适应检索，有触发词才执行 |
| Weibull 衰减批量扫描（遗忘调度） | < 50ms | partial index 仅扫活跃版本 |
| Skills BM25 检索（Top-5） | < 10ms | 内存 BM25 索引，无 SQLite IO |
| 成本按时间段 GROUP BY 聚合 | < 50ms | 覆盖索引扫描，无需回表 |
| 媒体任务状态轮询（TaskPoller） | < 5ms | status partial index 命中 |
| 向量 KNN 检索（Top-10，sqlite-vec） | < 200ms | 语义检索基准 |

## 六、EXPLAIN QUERY PLAN 验证方法

每次新增索引或修改查询后，必须运行以下验证步骤：

**步骤 1：运行 EXPLAIN QUERY PLAN**

```sql
EXPLAIN QUERY PLAN
SELECT e.id, e.title
FROM memory_entries e
WHERE e.workspace_id = 'ws-001'
  AND e.created_at >= '2025-01-01'
ORDER BY e.created_at DESC
LIMIT 50;
```

输出应包含 `USING INDEX idx_memory_ws_time`，而非 `SCAN memory_entries`（全表扫描）。若看到 `SCAN` 则索引未生效，需检查列顺序或查询条件。

**步骤 2：集成到 CI 的自动验证脚本**

```bash
# 在 scripts/check_query_plan.sh 中
sqlite3 /tmp/test.db < migrations/001_init.sql
sqlite3 /tmp/test.db "EXPLAIN QUERY PLAN \
  SELECT * FROM memory_entries \
  WHERE workspace_id='x' AND created_at>='2025-01-01';" \
| grep -q "USING INDEX" || { echo "FAIL: full table scan detected"; exit 1; }
```

**步骤 3：关注关键指标**

- `USING INDEX` — 索引命中，合格
- `USING COVERING INDEX` — 覆盖索引，无需回表，最优
- `SCAN ... (~N rows)` — 全表扫描，需优化
- FTS5 查询应出现 `SCAN memory_entries_fts VIRTUAL TABLE INDEX`

建议在 Rust 测试中使用 `sqlx::query("EXPLAIN QUERY PLAN ...")` 断言结果集不含 `SCAN` 关键字，作为回归门禁。
