# 存储诊断与跨进程设置验证

## 只读入口

Desktop：偏好设置 → 诊断 → 存储与配置。命令行：

```sh
cargo run -p home --bin astro-doctor -- --root /absolute/path/to/astro-home
```

不传 `--root` 时使用 `home::default_memory_dir()`。CLI 输出结构化 JSON；不修改配置、
不执行迁移、不清理文件，也不会为了检查一个不存在的数据根而创建它。
Tauri 的 `inspect_home_storage` 和 CLI 共用 `home::storage_diagnostics::inspect_home`。
该检查器与原来的 Backend/MCP/SQLite 运行健康卡片分离，不调用那些可能初始化数据库的 API。

状态区分：尚未初始化、可读取、需要目录迁移、需要可编辑设置迁移、迁移中断、
配置无效、不可读。没有 `desktop.settings_version` 不自动等于迁移失败：没有旧设置文件
时可以使用默认值。已标记迁移完成的旧 JSON 备份不会被重新当作运行配置。

检查根 `config.toml` 的语法与已知 Desktop 设置字段，不代表所有项目/include 分层配置、
Provider 网络连接或数据库健康已验证。配置异常只返回固定诊断代码和路径，不回传正文或
解析器中的敏感片段；不读取 `.env`、数据库、rollout 或浏览器内容。缓存目录、启用状态、
TTL 和容量是允许展示的策略字段；不回传缓存 payload。

## 扫描和资源检查边界

- 文件大小是逻辑字节数，不等于 APFS 实际占用；硬链接、压缩、稀疏文件可能影响差异。
- 每次最多检查 20,000 个条目、24 层目录，并使用约 2 秒的扫描预算；预算在条目间检查，
  不强制中断单次系统文件 I/O。达到上限或无法读取时显示部分结果，不冒充完整统计。
- 不跟随子目录/文件软链接，明确报告跳过数量。没有迁移版本且扫描不完整时，不能断言
  不存在旧 Agent 设置，因此不报告正常配置状态。
- 资源引用检查仅覆盖 UI 提供的当前/最近壁纸和 `ui/style/active.json` 中的活动壁纸。
  外部路径、越界路径和软链接标为未检查；图片缺失与配置损坏是不同问题。
- 不周期轮询，只在该面板激活和手动刷新时检查；异步请求按序号丢弃过时结果。

## 清理预览

检查和预览仍为只读。若需处理候选，可生成独立确认单，明确同意后将所列文件移入恢复区；
不提供永久删除或自动清空恢复区的 RPC。详见 [安全清理与恢复区](storage-cleanup.md)。

| 类别 | 预览策略 |
| --- | --- |
| 模型 / MCP 缓存 | 共用运行时 `[cache.models]` / `[cache.mcp]` 策略解析器，使用实际目录和 TTL；仅列入封装归属校验通过且过期的 Astro 缓存 |
| `logs/agent.log.YYYY-MM-DD`、`errors.log.YYYY-MM-DD` | 文件日期和修改时间均超过 30 天才列为候选 |
| 备份 | 人工审阅完整备份集，不按单文件自动删除 |
| 会话、rollout、数据库、工作区、技能、壁纸、浏览器登录数据、安全审计 | 保护；不进入自动候选列表 |

候选统计与展示样本分开，最多展示 30 个路径。候选不构成“立即删除安全”的保证，
没有做全量资源引用追踪或运行进程占用检查。数据迁移与恢复继续遵守
[目录布局](home-layout.md) 和 [全局设置](global-settings.md) 的显式工作流。

缓存预览额外验证 `astro-cache-v1-<domain>-<fingerprint>.json` 文件名与封装的版本、领域、
指纹和 `written_at`，依据运行时的 `now - written_at > ttl_seconds` 判断过期，不能只凭
mtime 或“文件放在缓存目录里”认定可清理。未知文件、未来时间戳、停用缓存均不列入。
为了验证完整 JSON，读取受限的缓存封装，但不构造或返回 payload 对象；单文件最多 512 KiB，
累计最多 8 MiB，超过预算或封装无效时标记预览不完整，数据不被删除或修改。

数据根内的自定义缓存目录可检查；外部目录只展示配置位置，不扫描，也不计入占用。
软链接、无法安全解析的目录及两个领域间重叠的目录不生成缓存候选。
缓存路径不能覆盖工作区、记忆、技能、UI、自动化、日志等持久化领域。
目录迁移和扩展迁移（`backups/extensions-in-progress.json`）的中断标记都纳入检查；
配置无效、迁移未完成等非正常状态下清空候选列表，保留占用和诊断信息。

## 保存 → 进程重启 → 读取

```sh
node tools/verify-settings-restart.mjs
```

脚本创建专属临时目录，逐次启动独立测试进程：

1. Desktop 实际的 `save_state`、工具/Skill 设置入口与 `AgentRuntimeConfig::save` 写入。
2. 新 Desktop 测试进程调用实际读取入口，验证模型、端点、活动 Provider、开关和 Agent 默认值。
3. 独立 Server 测试进程调用 Cron Provider 读取与目标解析。
4. 独立 Workflow 测试进程构造实际 Provider 配置表。

所有阶段使用相同临时数据根、虚构的本地 OpenAI-compatible 端点和测试占位 key，不发模型请求、不读取或替换真实
用户配置。测试还验证无旧 JSON 双写、外来 TOML 段和注释保持不变。
这些 fixture 默认 ignored，只有脚本显式运行；CI quality 工作流单独执行此脚本，并验证
每个阶段确实运行了一个测试，避免过滤名称失效导致“零测试通过”。

常规回归还包括：诊断进程不创建目录、不修复坏配置、不产生 WAL/SHM；清理候选不包含
受保护数据；现有首次启动/二次初始化与项目规则测试继续检查不生成旧目录或项目 `.astro/`。
