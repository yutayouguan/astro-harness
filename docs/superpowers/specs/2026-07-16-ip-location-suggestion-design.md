# IP 城市自动推测

日期：2026-07-16  
状态：设计已批准，待实施

## 目标

当 `request_user_location` 展示位置授权卡片时，通过公网 IP 自动推测城市并预填到城市输入框。用户仍需点击确认，推测失败时可继续手动输入。

天气查询只需要城市级精度。本功能不申请系统定位权限，也不替代现有的精确定位与拒绝操作。

## 方案

### 数据源与后端命令

- 新增独立 Tauri 命令 `infer_ip_location`，由 Rust 使用现有 `reqwest` 依赖请求 `https://ipwho.is/`。
- 设置短连接和总超时；仅接受成功响应中非空的 `city`。
- 命令返回稳定 DTO：城市、地区和国家。前端当前只使用城市，其余字段用于排错及后续本地化展示。
- 不读取、记录或持久化 IP；第三方服务会像任何公网服务一样看到请求出口 IP。
- 网络错误、限流、格式错误和空城市统一返回可识别错误，交由前端静默降级。

选择 Rust 后端请求而非浏览器直连，可避免 CORS，并将外部 API、超时和响应校验集中在一个边界内。高德 MCP 依赖用户配置 Key，不作为内置自动推测链路。

## 前端结构

新增位置卡片包装组件与小型 hook：

1. 仅当活动 surface 的 interrupt reason 为 `location_required` 时调用 `infer_ip_location`。
2. 请求期间显示“正在根据 IP 推测城市”；成功后显示“已根据 IP 推测，可修改后确认”。
3. 将返回城市作为 `A2UIRenderer` 的初始字段值传入，字段键为 `city`。
4. `A2UIRenderer` 支持可选 `initialFieldValues`。异步结果到达时，只填充仍为空的字段，绝不覆盖用户已输入的内容。
5. 同一位置卡片只请求一次；组件卸载后忽略迟到结果。

现有操作保持不变：

- `choose_city` 提交 `{ city }`
- `share_location` 继续尝试浏览器精确定位
- `deny` 提交 `{ denied: true }`

## 错误与隐私

- IP 推测失败不弹错误 toast，避免阻塞主流程；状态文案提示用户手动输入。
- 不把第三方服务错误详情暴露到界面。
- 不自动提交城市，防止 VPN、代理、运营商出口或企业网络导致误判。
- 不缓存到磁盘。组件生命周期内只发起一次请求。

## 测试

Rust：

- 成功响应解析城市、地区与国家。
- `success: false`、空城市及非法 JSON 返回错误。
- HTTP 状态异常和超时路径由请求边界覆盖。

前端：

- IP 城市会填入空的 `city` 字段。
- 用户先输入城市时，迟到的自动推测不会覆盖。
- 非位置 surface 不触发请求。
- 请求失败后城市输入和确认操作仍可用。

验收命令：

```bash
cd frontend && npm run build
cd frontend/src-tauri && cargo test
```

## 非目标

- 不接入 macOS Core Location。
- 不实现 GPS 或持续定位。
- 不自动调用天气 API。
- 不将城市写入用户偏好或记忆。
- 不要求或管理第三方 API Key。
