# 交互执行模式设计

> 版本：v1.0 | 日期：2026-08-07 | 状态：草稿
> 对应需求：F-39 交互执行模式、M-38 自适应执行模式

本文档是 F-39/M-38 在系统设计层的规范，描述**自适应规划**、**Pending 消息队列**、**YOLO 开关**、**MultiTask 并发**四个特性的完整交互流程与实现约束。后端实现见 [02-agent-runtime详细设计.md](02-agent-runtime详细设计.md)。

---

## 1. 三维控制体系回顾

| 维度 | 控制目标 | 触发时机 | 受 YOLO 影响 |
| ---- | -------- | -------- | ------------ |
| **自适应规划** | 任务复杂度 | LLM 调用后、工具执行前 | **否** |
| **L1/L2/L3 风险门控** | 工具风险 | 每次工具调用前 | **是（L2/L3 被跳过）** |
| **YOLO 开关** | 信任程度 | 用户主动开启/系统强制关闭 | — |

三者正交，任意组合均合法：YOLO ON 时计划确认仍正常弹出；L3 工具被 YOLO 跳过后，计划确认仍可能触发。

## 2. 自适应规划（Plan Confirmation）

### 2.1 触发条件

由 LLM 自判断，满足以下任一条件时在响应中输出 `<agent_plan>` 块：

- 预估工具调用步骤 > 3 步
- 涉及不可逆操作（`DeleteFile`、`NetworkWrite`、`ExecuteBash` 等 L3 工具）
- 需要派生子 Agent（`SpawnAgent`）
- 操作横跨多个工作区或影响系统级配置

LLM 通过系统提示词中注入的规划指令感知上述触发条件（见 `04-Prompt工程.md`）。

> **注意**：在详细设计阶段（`01-agent-core详细设计.md`），计划确认机制已从 `<agent_plan>` XML 块解析方式**改为 `submit_plan` 内置工具方式**。LLM 通过调用 `submit_plan` 工具提交执行计划，运行时拦截该工具调用并触发确认流程，取代了对 LLM 输出进行 XML 解析的做法。这种方式更可靠（利用结构化工具调用而非自由文本解析），且与现有工具调用审批流程统一。下文的 `<agent_plan>` XML 格式描述保留作为历史参考。

### 2.2 `<agent_plan>` 格式

```xml
<agent_plan>
  <summary>删除旧版本构建产物并重新编译项目</summary>
  <steps>
    <step id="1" tool="shell_exec" risk="L1">列出 target/ 目录内容</step>
    <step id="2" tool="file_delete" risk="L3">删除 target/ 下超过 30 天的文件（不可逆）</step>
    <step id="3" tool="shell_exec" risk="L1">执行 cargo build --release</step>
    <step id="4" tool="file_write" risk="L2">写入构建日志到 build.log</step>
  </steps>
  <estimated_duration>约 2 分钟</estimated_duration>
  <irreversible_steps>2</irreversible_steps>
</agent_plan>
```

### 2.3 事件流

```
后端（Planner）                         前端（React）
────────────────────────────────────────────────────
解析 <agent_plan>
    │
    ▼
emit "plan_confirmation_required"
    {steps, summary, irreversible_steps}   ──────────►  渲染 PlanConfirmDialog
                                                              ├─ 步骤列表（含风险标签）
                                                              ├─ 不可逆步骤高亮
                                                              └─ [确认] [修改] [取消]
                                           ◄──────────  invoke("confirm_plan", plan)
    │
    ├─ confirmed  → 继续工具执行
    ├─ modified   → 将修改后的计划文本重新注入 context 后继续
    └─ cancelled  → emit "plan_cancelled" → 本轮终止
```

### 2.4 Tauri 事件 / 命令

```typescript
// 后端 → 前端
interface PlanConfirmationPayload {
  conversationId: string;
  steps: { id: string; description: string; tool: string; risk: "L1" | "L2" | "L3" }[];
  summary: string;
  irreversibleSteps: number;
  estimatedDuration: string;
}
// event: "plan_confirmation_required"

// 前端 → 后端
// 确认计划（可编辑）
await invoke("confirm_plan", { requestId: string, editedPlan: string })

// 取消计划
await invoke("cancel_plan", { requestId: string })
```

## 3. Pending 消息队列

### 3.1 状态机

```text
用户在 Agent 运行中输入消息
    │
    ▼
[Agent 状态 = RUNNING？]
    ├─ YES → 消息进入 PendingQueue
    │         前端：输入框下方显示"等待执行中..."Badge
    │         消息气泡以半透明"Pending"样式渲染
    │
    └─ NO  → 正常发送，直接进入本轮 context
    │
    ▼（本轮 round_loop 结束）
PendingQueue::drain() → 注入下一轮 context
前端："等待执行中..."Badge 消失，消息气泡样式恢复正常
```

### 3.2 并发安全

`PendingQueue` 使用 `Arc<Mutex<Vec<PendingMessage>>>`，`push()` 和 `drain()` 不会竞争：
- `push()` 由 Tauri command 线程调用（前端触发）
- `drain()` 由 `round_loop` 任务线程调用（每轮开始时）

两者不会同时持锁（drain 完成后 round_loop 才开始 LLM 调用，此后 push 可安全写入新消息供下一轮使用）。

### 3.3 崩溃行为

队列为纯内存存储，崩溃时丢失。重启后 UI 显示 Banner 提示用户重新输入（见 PRD §4.4 异常处理）。

## 4. YOLO 开关

### 4.1 生命周期

```text
会话启动 → YOLO = OFF（强制初始值）
    │
    ▼ 用户点击 YOLO 开关
首次启用 → 弹出免责确认对话框
    │  [同意] → YOLO = ON
    │  [取消] → 保持 OFF
    │
    ▼ YOLO = ON 期间
工具执行 → HumanGuard 跳过 L2/L3 弹窗
审计日志 → decided_by = "yolo"，仍记录
    │
    ├─ 用户手动关闭 → YOLO = OFF
    ├─ 费用超限（BudgetManager Block）→ 强制 YOLO = OFF + 推送 yolo_force_disabled 事件
    └─ 会话结束 → YOLO 重置为 OFF（不持久化）
```

### 4.2 首次免责确认对话框

```text
╔══════════════════════════════════════════════════════╗
║  ⚡ 启用 YOLO 模式                                   ║
╠══════════════════════════════════════════════════════╣
║  YOLO 模式将跳过所有 L2/L3 工具调用的审批弹窗，     ║
║  Agent 将自动执行所有操作，包括：                    ║
║    • 写入/删除文件                                   ║
║    • 网络写操作                                      ║
║    • 派生子 Agent                                    ║
║                                                      ║
║  ⚠️  高风险操作将不再等待您的确认                    ║
║  📊  费用预算超限时自动关闭                          ║
║  📝  所有操作仍记录审计日志                          ║
║                                                      ║
║  [我理解风险，启用 YOLO]        [取消]               ║
╚══════════════════════════════════════════════════════╝
```

### 4.3 UI 状态指示

| YOLO 状态 | 工具栏显示 | 说明 |
| --------- | ---------- | ---- |
| OFF | ⚡ YOLO（灰色） | 默认，点击可开启 |
| ON | ⚡ YOLO（橙色，呼吸动画） | 提醒用户当前无审批拦截 |
| 强制关闭 | ⚡ YOLO（红色闪一下 → 回灰） | Toast 提示"费用超限，YOLO 已关闭" |

### 4.4 Tauri 事件 / 命令

```typescript
// 前端 → 后端
invoke("set_yolo", { enabled: boolean })

// 后端 → 前端（强制关闭时）
interface YoloForceDisabledPayload { reason: string }
// event: "yolo_force_disabled"
```

## 5. MultiTask 并发

### 5.1 隔离原则

不同工作区的 Agent 任务在同一进程内并发执行，通过以下机制隔离：

| 资源 | 隔离方式 |
| ---- | -------- |
| Agent 状态 | 每个任务独立 `AgentExecutor` 实例 |
| HumanGuard | 每个任务独立 `HumanGuard`（独立 YOLO + pending_decisions） |
| LLM 调用 | 共享 `ProviderRegistry`，Token 计数各自独立 |
| 费用统计 | 共享 `BudgetManager`，`workspace_id` 字段区分 |
| 审计日志 | 共享 `audit_logs` 表，`agent_task_id` 字段区分 |

### 5.2 侧边栏任务列表 UI

```text
┌─────────────────────────────────┐
│  🔄 正在执行的任务               │
├─────────────────────────────────┤
│  📂 project-alpha               │
│  ████████░░░░  步骤 3/5         │
│  [暂停]  [停止]                  │
├─────────────────────────────────┤
│  📂 research-ws                 │
│  ⚡ YOLO  正在搜索资料...        │
│  [暂停]  [停止]                  │
└─────────────────────────────────┘
```

### 5.3 审批弹窗队列

同一时刻多个任务均触发 L2/L3 弹窗时，前端将弹窗序列化展示（队列模式），用户逐一处理。每个弹窗标注所属工作区名称，避免混淆。
