# 记忆系统详细设计

> **Harness 当前基线（2026-09-07）**：`MemoryManager`（`crates/agent-memory`）管理 `MEMORY.md/USER.md`（位于 `~/.astro/agents/{agent_id}/`）、dreaming 管道、待审批记忆队列（`pending/`）和 decision log（JSONL）。`MemoryStore` 是有界分节文件存储（`\n§\n` 分隔符，MEMORY 上限 2200 字符、USER 上限 1375 字符），具有 live/snapshot 双态——`snapshot` 在会话内冻结直到显式 `refresh_snapshot()`。记忆工具名为 `memory`（通过 `dispatch_memory_tool` 分发）。Harness 在 `prepare_turn` 中按预算将快照/召回结果组装为带角色动态上下文（`PromptContract`）。本文中的 `memory_entries` SQLite 表、embeddings 虚拟表、向量衰减和全自动写入仅属目标设计。

## 1. 四层记忆架构

> **架构决策**：原五层设计中的 L5（用户建模）实质上是 L3 持久记忆的一个写入管道（推断引擎），而非独立存储层。简化为四层，降低认知复杂度。

| 层级 | 名称 | 实现 | 注入方式 |
| ---- | ---- | ---- | ---- |
| L1 | 情节记忆 | SQLite 对话表 + FTS5 | session_search 工具按需检索 |
| L2 | 语义记忆 | embeddings 虚拟表 + FTS5 | @ 引用按需检索 |
| L3 | 持久记忆 | MEMORY.md（Agent 笔记）+ USER.md（用户画像，由 LLM 推断引擎自动维护） | 会话开始冻结注入 |
| L4 | 程序性记忆 | Skills BM25 索引（tantivy） | 渐进式披露 |

用户建模功能集成在 L3 中：`USER.md` 的内容由 LLM 推断引擎在会话结束时自动更新（通过 `memory` 工具），不再作为独立的第五层。

## 2. 情节记忆（Episodic）

Agent 历史由 `ResponseItem` 表示（`agent-protocol` crate），通过 rollout JSONL 持久化。`SessionStore`（`state.db`）为可重建投影；rollout 是权威历史。`TurnContext` / `StepContext` 提供层级上下文。

**消息格式**：Agent、rollout、SQLite 和 Desktop history RPC 都使用 `ResponseItem`。相邻的 user/assistant message item 不得重复角色，由 `validate_message_order()` 强制。

**工具上下文压缩**：`maintain_tool_context()` 按三阶段处理工具结果：prune → `AuxiliaryTask::Compaction` LLM 摘要 → head/tail fallback。`content` 始终保留原文，`compressed_content` 是 Provider 视图。工具结果超过 `DEFAULT_SPILL_THRESHOLD_BYTES`（16KB）时落盘，provider history 用 stub。详见 `02-上下文压缩算法设计.md`。

压缩算法优先选择"摘要保留法"：将最早的若干轮对话发送给 LLM 生成摘要，以单条 `role: user` 系统摘要消息替换原始片段，保留 system prompt、最近 10 轮、所有 tool_result 消息不压缩。压缩前将原始消息持久化到 SQLite `conversations` 表，确保可追溯。

## 3. 语义记忆（Semantic）

### 3.1 写入前噪音过滤

蒸馏提取出的候选片段在写入 `memory_entries` 前，先经过规则引擎过滤，命中任意一条即丢弃，**无需 LLM 判断**：

```rust
fn is_noise(content: &str) -> bool {
    let s = content.trim();
    // 1. 极短内容（< 3个字符）
    if s.chars().count() < 3 { return true; }
    // 2. 肯定/否定回复
    const TRIVIAL: &[&str] = &["ok","okay","好","好的","嗯","对","是","可以","不","不行","没问题","收到"];
    if TRIVIAL.iter().any(|&t| s.eq_ignore_ascii_case(t)) { return true; }
    // 3. 纯表情符号
    if s.chars().all(|c| c.is_ascii_punctuation() || unic_emoji_char::is_emoji(c) || c.is_whitespace()) { return true; }
    // 4. 系统命令（! / 开头）
    if s.starts_with('!') || s.starts_with('/') { return true; }
    // 5. 重复短语（同一字符/词连续出现≥3次，如"哈哈哈"、"啊啊啊"）
    if is_repetitive(s) { return true; }
    false
}
```

实测噪音占比约 40%，过滤后内存减少约 40%，KNN 检索质量同步提升。

### 3.2 记忆安全扫描

所有写入持久记忆的内容在入库前必须通过安全扫描，防止恶意内容被持久化后在每次 session 注入：

```rust
pub struct MemorySecurityScanner;

impl MemorySecurityScanner {
    pub fn scan(value: &str) -> Result<(), MemoryScanError> {
        // 1. Prompt 注入检测
        let injection_patterns = [
            r"(?i)ignore\s+(all\s+)?previous\s+instructions",
            r"(?i)you\s+are\s+now\s+a",
            r"(?i)system\s*:\s*you\s+are",
            r"<\|system\|>",
            r"<\|im_start\|>",
            r"(?i)忽略.*之前.*指令",
            r"(?i)你现在是.*助手",
            r"(?i)从现在开始.*角色",
        ];
        for pattern in &injection_patterns {
            if Regex::new(pattern).unwrap().is_match(value) {
                return Err(MemoryScanError::PromptInjection(pattern.to_string()));
            }
        }
        
        // 2. 凭证泄露检测
        let credential_patterns = [
            r"(?i)(sk|ak|api[_-]?key)[_-]?[a-zA-Z0-9]{20,}",  // API Key
            r"(?i)password\s*[:=]\s*\S{8,}",                     // 密码
            r"(?i)(secret|token)\s*[:=]\s*\S{16,}",              // Secret/Token
            r"-----BEGIN\s+(RSA\s+)?PRIVATE\s+KEY-----",         // 私钥
        ];
        for pattern in &credential_patterns {
            if Regex::new(pattern).unwrap().is_match(value) {
                return Err(MemoryScanError::CredentialLeak(pattern.to_string()));
            }
        }
        
        // 3. 不可见 Unicode 检测（隐写攻击）
        if value.chars().any(|c| {
            matches!(c,
                '\u{200B}'..='\u{200F}' |  // 零宽字符
                '\u{202A}'..='\u{202E}' |  // 方向控制
                '\u{2060}'..='\u{2069}' |  // 不可见格式
                '\u{FEFF}'                  // BOM
            )
        }) {
            return Err(MemoryScanError::InvisibleUnicode);
        }
        
        Ok(())
    }
}
```

在 `memory` 工具的 Add 和 Replace 操作中，调用此扫描器：

```rust
// 安全扫描（在噪声过滤之后、写入数据库之前）
MemorySecurityScanner::scan(&value)?;
```

### 3.3 写入流程

过滤通过后：批量调用 Embedding Provider 生成向量，`INSERT INTO embeddings(source_id, source_type, workspace_id, embedding)` 写入 sqlite-vec 虚表，`source_id` 与 `memory_entries.id` 对应。批量写入以 32 条为一批。

**Embedding 生成**：优先 OpenAI `text-embedding-3-small`（维度 1536）；本地模型使用 `nomic-embed-text`（维度 768）。维度差异通过 embeddings 虚拟表的向量列定义隔离，不同维度的向量存储在独立的 vec0 虚拟表中，禁止跨维度比较。

### 3.4 自适应检索

**并非每轮对话都需要检索记忆**。只有用户输入中出现"回忆触发词"时才执行 KNN，其余情况跳过，可降低约 60% 的无效检索：

```rust
const TRIGGER_KEYWORDS: &[&str] = &[
    "我之前说过", "你还记得", "上次", "之前提到", "以前说",
    "记得吗", "历史", "之前我们", "上一次", "你知道我",
];

fn needs_memory_retrieval(input: &str) -> bool {
    TRIGGER_KEYWORDS.iter().any(|kw| input.contains(kw))
}
```

触发时执行 KNN（仅查询 `valid_to IS NULL` 的当前版本）：

```sql
SELECT e.source_id, e.distance, me.key, me.value, me.category
FROM embeddings e
JOIN memory_entries me ON e.source_id = me.id
WHERE e.embedding MATCH ?1
  AND e.workspace_id = ?2
  AND e.source_type = 'memory'
  AND me.valid_to IS NULL
  AND e.k = 8
ORDER BY e.distance;
```

检索结果注入 system prompt 的 `<memory>` 块；命中的条目异步更新 `retrieval_count` 和 `last_retrieved_at`。

## 4. 持久记忆（Persistent）

**注入时机**：Session 启动时读取 `MEMORY.md`（上限 2,200 tokens）和 `USER.md`（上限 1,375 tokens）的全文，拼接为 system prompt 前缀的固定块，**整个 session 内不再更新**。

**不在 session 内更新的原因**：Anthropic Prompt Cache 基于 system prompt 前缀做缓存命中判断。若 session 中途修改该块，缓存 prefix 发生变化，导致后续所有请求 cache miss，Token 成本显著上升。冻结快照策略可保证同一 session 内 cache prefix 完全稳定。

**文件大小限制**：`MEMORY.md` 上限 2,200 tokens，`USER.md` 上限 1,375 tokens，两者合计控制在 3,575 tokens 以内，为工具调用和对话历史留足空间。

**更新时机**：`memory` 工具通过 `MemoryManager.handle_memory_op()` 直接操作文件存储（`MemoryStore` 的 `live` 状态写入磁盘），但 `snapshot` 保持冻结。文件系统的 `MEMORY.md` / `USER.md` 变更在当前 session 的 prompt 注入中不可见（冻结快照），下次 Session 启动时重新加载。

### 容量执行机制

**检查时机**：在 `memory` 工具的 Add 操作写入后。

**检查方式**：

```rust
pub async fn check_capacity(
    tx: &mut SqliteTransaction,
    workspace_id: &str,
) -> Result<CapacityStatus, MemoryError> {
    // 计算当前活跃条目的 value 字段总 token 数
    let total: i64 = sqlx::query_scalar(
        "SELECT COALESCE(SUM(LENGTH(value)), 0) FROM memory_entries 
         WHERE workspace_id = ? AND valid_to IS NULL AND source != 'user_model'"
    )
    .bind(workspace_id)
    .fetch_one(&mut **tx).await?;
    
    let user_total: i64 = sqlx::query_scalar(
        "SELECT COALESCE(SUM(LENGTH(value)), 0) FROM memory_entries 
         WHERE workspace_id = ? AND valid_to IS NULL AND source = 'user_model'"
    )
    .bind(workspace_id)
    .fetch_one(&mut **tx).await?;
    
    let memory_limit = 3000; // MEMORY.md 字符上限
    let user_limit = 1375;   // USER.md 字符上限
    
    if total > memory_limit {
        return Ok(CapacityStatus::MemoryExceeded { used: total, limit: memory_limit });
    }
    if user_total > user_limit {
        return Ok(CapacityStatus::UserExceeded { used: user_total, limit: user_limit });
    }
    if total > memory_limit * 80 / 100 {
        return Ok(CapacityStatus::MemoryWarning { used: total, limit: memory_limit });
    }
    Ok(CapacityStatus::Ok)
}
```

**超出限制时的处理**：

- **80% 警告**：工具返回成功，但附加提示 "记忆容量已达 80%，建议整合相关条目"
- **100% 超出**：工具返回错误，附带当前所有活跃条目列表供 Agent 决定删除/整合哪些
- 不自动删除——让 Agent（或用户）主动决定保留策略

### MEMORY.md / USER.md 生成规则

Session 初始化时，从 `memory_entries` 表生成冻结快照文件：

**MEMORY.md 生成**：

```sql
SELECT key, value, category FROM memory_entries
WHERE workspace_id = ? AND valid_to IS NULL AND source != 'user_model'
ORDER BY importance DESC, created_at DESC
```

按 category 分组格式化：

```markdown
## 工作模式
- [key]: value

## 案例教训  
- [key]: value

## 核心洞察
- [key]: value

## 日常事件
- [key]: value
```

**USER.md 生成**：

```sql
SELECT key, value FROM memory_entries
WHERE workspace_id = ? AND valid_to IS NULL AND source = 'user_model'
ORDER BY importance DESC
```

格式化为用户画像：

```markdown
## 用户画像
- 技术水平: value
- 偏好语言: value
- 工作领域: value
```

### System Prompt 注入格式

MEMORY.md 和 USER.md 在 System Prompt 的第 4 槽位（记忆上下文）注入，格式如下：

```text
<memory usage="67%" chars="2010/3000">
[MEMORY.md 内容]
</memory>

<user_profile usage="45%" chars="619/1375">
[USER.md 内容]
</user_profile>
```

**首次运行（空记忆）**：注入引导提示：

```text
<memory usage="0%" chars="0/3000">
暂无持久记忆。请在对话中使用 memory 工具主动记录用户偏好、项目上下文等重要信息。
</memory>
```

**注入位置**：在 SOUL.md（槽位 1）和工作区 Prompt（槽位 2）之后、Skills 指南（槽位 5）之前。这保证了记忆前缀的稳定性，最大化 Anthropic Prompt Cache 命中率。

## 5. 程序性记忆（Procedural）

**BM25 索引结构**：Skills 加载后使用 `tantivy` crate 构建内存 BM25 索引（与 `../04-工具与扩展生态/01-Skills系统详细设计.md` 保持一致）。每个 `.md` 文件的标题和描述作为文档写入 tantivy 内存索引，利用 tantivy 内置的 BM25 评分和分词器（支持中英文混合分词）。查询时对用户输入执行 tantivy 全文检索，按 BM25 分数排序，返回 Top-3 相关技能注入 prompt。

**热加载**：使用 `notify` crate 监听 `~/.astro/skills/` 目录的 `Create`、`Modify`、`Remove` 事件，触发后在后台线程重建 tantivy 索引。

**增量 vs 全量策略**：单文件变更时做增量更新（tantivy `IndexWriter` 先 delete_term 再 add_document）；若变更文件数超过总量 30% 或发生目录重命名，则丢弃旧索引并执行全量重建，避免增量累积错误。

## 6. 用户建模（User Model）

**LLM 推理触发条件**：累计对话轮数达到阈值（默认每 20 轮）；或用户消息中检测到显著偏好表达关键词（"我更喜欢"、"以后都"、"不要再"等）时，提前触发一次用户画像推断。

**USER.md 更新策略**：推断时将现有 `USER.md` 内容与本次新观察一并发送给 LLM，要求以"合并更新"模式输出，保留已有结论、追加新发现、删除已过期条目，而非全量重写，避免历史信息丢失。

**去抖动机制**：Session 内多次触发的画像更新结果暂存内存，Session 结束时统一执行一次写入 SQLite 和文件系统，防止高频写入造成磁盘 I/O 抖动与 cache 失效。

## 7. 记忆更新策略

记忆更新的核心原则：**同一事实只保留一条记录**，新信息优先通过 patch 覆盖旧记录，而非追加新条目，避免语义记忆因时间推移积累大量互相矛盾的碎片。

### 7.1 写入前矛盾检测

每次 `memory(action=add)` 执行前，先对待写入内容做 KNN 查询（k=5，余弦距离 < 0.15，即高度相似），将命中的旧条目与新内容一并提交给 LLM 判断：

```text
prompt: "新记忆：{new_content}\n已有记忆：{existing_list}\n
是否存在逻辑矛盾或信息过时？若是，指定需替换的条目 ID；若仅补充，返回 null。"
```

- LLM 返回需替换的 `id` → **软替换**：将旧条目标记 `valid_to = now()`、`superseded_by = new_id`，再 INSERT 新条目（新条目 `valid_from = now()`，`valid_to = NULL`）
- LLM 返回 `null`（纯补充信息）→ 直接 INSERT 新条目
- LLM 调用出错 → 降级为直接 INSERT，不阻断写入流程

**软替换而非硬覆盖**的优势：旧版本数据完整保留，可追溯"变之前是什么、什么时候变的、变成了什么"，排查问题时极有价值。查询时只取 `valid_to IS NULL` 的当前版本，历史版本对 Agent 不可见。

```rust
async fn soft_replace(tx: &mut Tx, old_id: &str, new_content: &str) -> Result<String> {
    let new_id = Uuid::new_v4().to_string();
    let now = now_ms();
    // 1. 关闭旧版本
    sqlx::query!("UPDATE memory_entries SET valid_to=?, superseded_by=? WHERE id=?",
        now, new_id, old_id).execute(&mut *tx).await?;
    // 2. 插入新版本（继承 category/key/half_life_days）
    sqlx::query!("INSERT INTO memory_entries (id, ..., valid_from) SELECT ?, ..., ? FROM memory_entries WHERE id=?",
        new_id, now, old_id).execute(&mut *tx).await?;
    Ok(new_id)
}
```

> **架构决策**：矛盾检测为**同步阻塞**操作，在 `memory` 工具的 Add 流程内执行。虽然增加了约 20ms 延迟（KNN 查询 + 相似度比较），但避免了异步竞态问题：同一 session 内快速写入矛盾记忆时，后写入的条目可以立即检测到先写入的条目并触发软替换。

矛盾检测流程（事务内）：

1. 对新内容生成 embedding
2. KNN 查询 Top-3 相似条目（cosine distance < 0.15）
3. 若存在高相似条目，自动执行 soft_replace（新版本取代旧版本）
4. 若无相似条目，正常插入

### 7.2 检索命中后自动更新

KNN 查询结果返回后，批量更新命中条目的检索统计：

```sql
UPDATE memory_entries
SET retrieval_count   = retrieval_count + 1,
    last_retrieved_at = unixepoch('now','subsec') * 1000
WHERE id IN (/* 本次命中的条目 ID 列表 */);
```

此更新在主流程返回后异步执行（tokio::spawn），不影响响应延迟。`retrieval_count` 和 `last_retrieved_at` 是遗忘策略的关键输入。

### 7.3 USER.md 差量更新

用户画像推断结果以 **diff-patch** 方式写入，而非全量覆盖：LLM 收到 `(现有 USER.md, 新观察)` 后输出结构化 patch（`add / modify / remove` 操作列表），Rust 层逐条应用，保留未涉及的历史结论，避免"下一次推断清空上一次结论"的问题。

## 8. 主动遗忘策略

遗忘（forget）与存储同等重要：无用记忆拖慢 KNN 检索、污染 prompt 注入内容，并可能违反用户隐私期望。

### 8.1 TTL 过期清理

`memory_entries.expires_at` 非 NULL 时表示该条目具有时效性。`EvolutionScheduler` 每次 Session 启动时执行：

```sql
DELETE FROM memory_entries WHERE expires_at < unixepoch('now','subsec') * 1000;
-- embeddings 对应行通过 trigger 或后置清理同步删除
```

适用场景：会议日程、临时代办、短期任务上下文（写入时主动设置 `expires_at`）。

### 8.2 Weibull 衰减剪枝

用 **Weibull 衰减函数**替代固定阈值，更接近人脑记忆的自然遗忘曲线：

```text
score = exp( -( age_days / effective_half_life )^1.5 )
```

其中 `effective_half_life` 根据 **记忆类型（category）** 和 **检索频率** 动态计算：

```rust
fn weibull_score(age_days: f64, category: &str, retrieval_count: u32) -> f64 {
    let base_half_life = match category {
        "daily_event"   => 14.0,   // 日常事件：今天调了个配置
        "case_lesson"   => 30.0,   // 案例教训：踩过的坑
        "work_pattern"  => 120.0,  // 工作模式：项目偏好、工作习惯
        "core_insight"  => 365.0,  // 核心洞察：底层原则、价值观
        _               => 30.0,
    };
    // 检索频率因子：未被检索的记忆不延长半衰期，频繁检索的记忆最多延长 3 倍
    let freq_factor = 1.0 + (retrieval_count as f64).ln_1p().min(2.0);
    // retrieval_count=0 → factor=1.0（不延长）
    // retrieval_count=1 → factor=1.69
    // retrieval_count=5 → factor=2.79
    // retrieval_count=10+ → factor=3.0（上限）
    let effective_half_life = base_half_life * freq_factor;
    (-(age_days / effective_half_life).powf(1.5)).exp()
}
```

| 记忆类型 | 半衰期 | 举例 |
| --- | --- | --- |
| 日常事件 `daily_event` | 14 天 | 今天调了个配置 |
| 案例教训 `case_lesson` | 30 天 | 踩过的坑 |
| 工作模式 `work_pattern` | 120 天 | 项目偏好、工作习惯 |
| 核心洞察 `core_insight` | 365 天 | 底层原则、价值观 |

> **版本分期实施**：
>

每次 Session 结束，`EvolutionScheduler` 对所有 `valid_to IS NULL` 的活跃条目计算当前 score，score < 0.05（接近完全遗忘）且存在超过 7 天的条目软删除（标记 `valid_to = now()`，不物理删除）：

```rust
let candidates = fetch_active_memories(workspace_id).await?;
for m in candidates {
    let age = (now_ms() - m.created_at) as f64 / 86_400_000.0;
    let score = weibull_score(age, &m.category, m.retrieval_count);
    if score < 0.05 && age > 7.0 && m.distilled_at.is_none() {
        soft_expire(&mut tx, &m.id).await?;
        write_audit_log(&mut tx, "memory_prune", &m.id, score).await?;
    }
}
```

软删除的条目对 Agent 不可见，但在调试面板可查看和撤销（24h 内可恢复）。

### 8.3 蒸馏后清理

语义记忆蒸馏至持久层（`MEMORY.md`）后，源条目将 `distilled_at` 标记为当前时间而非立即删除。蒸馏后 3 天（确认持久层稳定）再由定期清理任务删除，防止持久层写入异常时语义层已被清空。

```sql
DELETE FROM memory_entries
WHERE distilled_at IS NOT NULL
  AND distilled_at < (unixepoch('now') - 3*86400) * 1000;
```

### 8.4 用户主动遗忘

提供两种用户触发路径：

| 操作 | 触发方式 | 行为 |
| --- | --- | --- |
| 删除单条记忆 | `memory(action=remove, content=...)` | 从 `MemoryStore` 中移除匹配条目 |
| 工作区记忆清空 | Settings > Memory > 清空工作区记忆 | 删除该 `workspace_id` 下全部 `memory_entries`，重置 `embeddings` |
| 隐私模式一键清除 | Settings > Privacy > 清除所有记忆 | 同上，并额外清空 `MEMORY.md` / `USER.md` 文件内容 |

清空操作不可直接撤销，执行前需用户二次确认，完成后发送 `astro://memory/cleared` 事件。

## 9. 跨层蒸馏机制

**情节→语义**：每次对话结束后，`EvolutionScheduler` 从 `conversations` 表读取本次会话消息，调用 LLM 提取 3~5 个关键知识片段，生成 embedding 后批量写入 `memory_entries` + `embeddings`，标注 `source: episodic_distill`。

**语义→持久**：每 N 次对话（默认 N=10）或重要度评分超过阈值的条目积累到 5 条时，调度器将高分条目汇总后调用 LLM 提炼为简洁事实，追加至 `MEMORY.md` 草稿，下次 Session 启动时生效。

**调度协调**：`EvolutionScheduler` 在主线程 event loop 外以独立 Tokio task 运行，通过 `mpsc` channel 接收蒸馏任务，串行执行避免并发写冲突，同时向 UI 发送进度通知供调试面板展示。

```rust
async fn dispatch_memory_tool(ops: Vec<MemoryOp>) -> Result<ToolOutput, ToolError> {
    let mut tx = db.begin().await?;

    let mut added_ids: Vec<String> = vec![];

    for op in &ops {
        match op {
            MemoryOp::Add { workspace_id, key, value, category, importance, source } => {
                let id = Uuid::new_v4().to_string();
                sqlx::query!(
                    "INSERT INTO memory_entries (id, workspace_id, key, value, category, importance, source, created_at)
                     VALUES (?, ?, ?, ?, ?, ?, ?, (unixepoch('now','subsec')*1000))",
                    id, workspace_id, key, value, category, importance, source
                )
                .execute(&mut *tx).await?;
                added_ids.push(id.clone());
                write_audit_log(&mut tx, "add", &id, value).await?;
            }
            MemoryOp::Replace { id, value } => {
                // 软替换：将旧版本标记为过期，创建新版本
                let new_id = Uuid::new_v4().to_string();
                let now_ms = now_unix_ms();
                
                // 1. 过期旧版本
                sqlx::query(
                    "UPDATE memory_entries SET valid_to = ?1, superseded_by = ?2 WHERE id = ?3 AND valid_to IS NULL"
                )
                .bind(now_ms).bind(&new_id).bind(&id)
                .execute(&mut *tx).await?;
                
                // 2. 从旧版本复制元数据，创建新版本
                sqlx::query(
                    "INSERT INTO memory_entries (id, workspace_id, key, value, source, category, importance, half_life_days, valid_from, created_at)
                     SELECT ?1, workspace_id, key, ?2, source, category, importance, half_life_days, ?3, ?3
                     FROM memory_entries WHERE id = ?4"
                )
                .bind(&new_id).bind(&value).bind(now_ms).bind(&id)
                .execute(&mut *tx).await?;
                
                // 3. 生成新 embedding 并写入 embeddings 虚拟表
                let embedding = self.embed(&value).await?;
                sqlx::query(
                    "INSERT INTO embeddings (source_id, source_type, workspace_id, embedding)
                     VALUES (?1, 'memory', ?2, ?3)"
                )
                .bind(&new_id).bind(&workspace_id).bind(&embedding)
                .execute(&mut *tx).await?;
                
                replaced_ids.push(new_id);
            }
            MemoryOp::Remove { id } => {
                sqlx::query!("DELETE FROM memory_entries WHERE id = ?", id)
                    .execute(&mut *tx).await?;
                sqlx::query!("DELETE FROM embeddings WHERE source_id = ? AND source_type = 'memory'", id)
                    .execute(&mut *tx).await?;
                write_audit_log(&mut tx, "remove", *id, "").await?;
            }
        }
    }
```

**事务边界**：所有 `memory_entries` 的增删改与 `audit_log` 写入在同一数据库事务内完成，任一步骤失败则全部回滚，保证数据一致性。`embeddings` 的删除也包含在事务内（sqlite-vec 虚表支持事务），而新增条目的向量写入放在事务提交后异步执行，避免 embedding 网络请求阻塞事务锁。

**embedding 异步更新**：`tokio::spawn` 启动独立 task，调用 Embedding Provider 生成向量后执行 `INSERT INTO embeddings(source_id, source_type, workspace_id, embedding) VALUES (?, 'memory', ?, ?)`。若此步骤失败，`memory_entries` 数据已持久化，下次 Session 初始化时由修复任务补全缺失的向量。

**audit_log 写入时机**：在每条操作执行后、事务提交前立即写入 `audit_log` 表，记录操作类型、目标 ID、内容摘要和时间戳，与主操作原子提交，确保日志与数据状态完全一致。
