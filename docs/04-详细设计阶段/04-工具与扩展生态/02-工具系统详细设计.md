# 工具系统详细设计

> **当前实现基线（2026-09-07）**：唯一主链是 `CoreToolRuntime / ToolExecutor -> ToolRegistry -> ToolRouter -> StepContext -> Prompt.tools -> ResponsesRequest -> ResponseItem -> ToolRegistry::dispatch`。内置 inventory、MCP、Workflow/Extension 与 Skill 最终都汇入该链，不保留旧 handler table、`LegacyToolAdapter`、`BuiltinToolHandler`、`dispatch_tool` 或按 MCP 前缀直接执行的旁路。

> 阶段：详细设计
> 状态：当前代码契约
> 对应模块：`agent-types::tool_entry`、`agent-tools::engine`、`agent-core::runtime`

---

## 1. 不变量

1. `ToolRegistry` 同时拥有 `ToolEntry` 元数据与 `Arc<dyn CoreToolRuntime>`；可执行工具不能只有 schema。
2. 单次采样使用冻结的 `ToolRouter`；热重载、Skill 激活和 MCP 变化只影响后续 Step。
3. `routes` 是完整可执行集合，`model_routes` 是模型可直接调用的子集，两者不可混用。
4. 模型可见性、调用授权和执行能力是三个独立判断；可见不等于获批，获批不扩大 sandbox。
5. 原生工具调用与 matching output 必须按 `call_id` 写入 canonical `ResponseItem` 历史。
6. 未注册 runtime、非法参数、重复原生身份和未经发现的 Deferred 工具一律 fail closed。

## 2. 核心类型

### 2.1 `ToolName`

```rust
pub enum ToolName {
    Plain(String),
    Namespaced { namespace: String, name: String },
}
```

`None`、空 namespace 和 `functions` 等价于默认 function namespace。MCP 等原生 namespace 必须完整保留，不能只比较展平字符串。

### 2.2 `ToolEntry`

`ToolEntry` 是 Registry 的元数据事实源，主要字段包括：

- 内部注册键 `name` 与可选模型子名称 `model_name`；
- `namespace`、`description`、JSON `schema` 或 `freeform_format`；
- `toolset`、`check_fn` 与 `ToolExposure`；
- `needs_confirmation`、`approval_requirement`、`sandbox_preference`；
- MCP 专用 `mcp_approval` 与 `output_token_limit`。

### 2.3 `ToolExecutor` 与 `CoreToolRuntime`

```rust
pub trait ToolExecutor: Send + Sync + 'static {
    fn tool_name(&self) -> ToolName;
    fn spec(&self) -> ToolSpec;
    fn description(&self) -> &str;
    fn toolset(&self) -> &str;
    fn approval_requirement(&self) -> ExecApprovalRequirement;
    fn icon(&self) -> &'static str;
    fn handle<'a>(
        &'a self,
        ctx: &'a mut ToolContext<'_>,
        args: &'a serde_json::Value,
    ) -> ToolExecutorFuture<'a>;
}

pub trait CoreToolRuntime: ToolExecutor {}
```

### 2.4 `ToolOutput`

运行时结果使用三种基础结构和一个 metadata 包装：

- `Text(String)`；
- `Media { text, assets }`；
- `FileChanges { text, changes }`。
- `WithMetadata { output, metadata }`：有界、host-only 的结果元数据，不改变模型可见文本。

原始结果可用于审计和持久化；Provider 视图可以经过 hook、预算、spill 和压缩处理，但不能破坏 call/output 配对。文本替换必须保留 media、file changes 与 metadata；metadata 超过 16 KiB 时持久化省略标记，并在 Provider wire 边界移除。

## 3. 注册模型

### 3.1 内置工具

每个内置模块调用 `submit_builtin_tool!`。宏为该模块生成原生 `ToolExecutor` 实现和 inventory registrar：

```text
module register(ToolEntry metadata)
  + submit_builtin_tool!(dispatch function)
  -> generated ToolExecutor
  -> BuiltinToolRegistrar::register
  -> ToolRegistry::register_runtime(metadata, runtime)
```

`register_all()` 遍历 inventory，先拒绝跨 registrar 的重复注册名，再执行每个 registrar。测试要求每个元数据条目都存在 runtime，并且名称、描述、toolset、图标和审批要求一致。

### 3.2 动态工具

MCP、Workflow 和 Extension 等运行时发现的工具使用 `register_dynamic()` 或直接 `register_runtime()`：

```text
ToolEntry + DynToolHandler
  -> DynamicToolAdapter
  -> Arc<dyn CoreToolRuntime>
  -> ToolRegistry
```

更新元数据时会移除旧 runtime；热重载必须重新注册二者，防止旧执行器与新 schema 错配。

## 4. 暴露与发现

| `ToolExposure` | 模型初始可见 | `tool_search` 可发现 | 内部可路由 |
| --- | --- | --- | --- |
| `Direct` | 是 | 否（已直接可见） | 是 |
| `Deferred` | 否 | 是 | 被发现后是 |
| `Hidden` | 否 | 否 | 仅显式内部路径 |
| `DirectModelOnly` | 是 | 否（已直接可见） | 是 |
| `DeferredModelOnly` | 否 | 是 | 被发现后是 |

`schemas_for_step_with_mode()` 同时计算：

- 当前模型直接可见的 schema；
- durable `ToolSearchOutput` 已发现的 Deferred schema；
- Code Mode 可在 `exec` 内调用但不能由模型顶层直接调用的 nested schema。

不支持原生 `tool_search` 的模型只允许对 `allow_eager_fallback=true` 的 Deferred 工具做 eager 降级。Workflow 等明确禁止 eager fallback 的工具保持不可见。

## 5. Step 冻结与执行链

```text
capture_step_context
  -> reload_tools_and_mcp
  -> freeze ExtensionSnapshot + tool gates + Registry
  -> discovered_deferred_tool_names(canonical history)
  -> build_tool_router / finalize_tool_router
  -> ToolRouter { registry, routes, model_routes, model_visible_specs }
  -> build_prompt -> Prompt.tools -> ResponsesRequest.tools
  -> provider returns native ResponseItem call
  -> ToolRouter::build_tool_call
  -> model_can_call / routes_tool
  -> interaction mode + approval + sandbox attempt
  -> ToolRouter::dispatch
  -> ToolRegistry::dispatch
  -> CoreToolRuntime::handle
  -> TransformToolResult / PostToolUse / output budget
  -> matching ResponseItem output by call_id
  -> rollout + SessionStore projection
```

热重载或工具激活不能修改已经冻结的 Step。若模型调用不在 `model_routes` 中，调用在进入 runtime 前被拒绝。

## 6. 命名空间与内部键

| 来源 | 模型身份 | Registry 内部键 |
| --- | --- | --- |
| 默认 function | `(functions, name)` 或无 namespace | `name` |
| Browser/Media 等 namespace | `(namespace, child_name)` | 模块定义的 registered name |
| MCP | `(mcp__server, native_name)` | `mcp__server__native_name` |
| Workflow | `(workflow, workflow_name)` | Workflow 注册键 |

`ToolRouter` 负责从原生身份回映射内部键。执行层不得通过字符串前缀猜测 Server 或绕过 Router。

## 7. MCP 链路

```text
ExtensionSnapshot.mcp_servers
  -> McpHub::reload_with_configs
  -> initialize + tools/list
  -> enabled_tool_entries
  -> register_mcp_tool_entries
  -> ToolRegistry::register_dynamic(ToolEntry, DynamicToolAdapter)
  -> Step ToolRouter freezes native namespace route
  -> MCP approval / HITL
  -> ToolRegistry::dispatch
  -> DynamicToolAdapter::handle
  -> McpHub::call_tool -> Peer::call_tool
  -> raw output_token_limit
  -> hooks -> final output_token_limit
  -> matching ResponseItem output
```

普通 MCP tools 与 `mcp_resources` / `mcp_prompts` broker 都必须同时注册元数据和 runtime。MCP 配置、连接健康状态或 `tools/list_changed` 发生变化时，Registry 在后续 Step 重建。

---

## 8. Skill 链路

```text
ExtensionSnapshot.skill_index
  -> system prompt contains enabled Skill name + description
  -> skills(action=load|view, skill_id, input)
  -> ToolRegistry::dispatch -> native skills runtime
  -> load_skill_by_name_with_config
  -> raw ToolOutput("# Skill: ...")
  -> parse astro_tools from the same frozen config
  -> activate_skill_toolsets (additive)
  -> hooks + matching ResponseItem output
  -> next capture_step_context
```

只有成功的 `load/view` 激活 `astro_tools`；`list`、`curate`、`manage` 不激活。`ToolRegistry::dispatch` 不做 Skill soft-alias，防御性改写只存在于 `agent-core` 工具处理层，且不能绕过 `model_routes`。

---

## 9. 审批、沙箱与结果

- interaction mode 在执行前过滤 action；Plan 模式禁止 Skill manage 等写操作。
- MCP approval 先读取单工具策略，再读取 Server 默认策略，并受 Session 审批上限约束。
- 进程工具使用 attempt-scoped sandbox；MCP STDIO 连接使用 Session 解析出的连接权限快照。
- `PreToolUse` 可以阻止或修改输入；`TransformToolResult` / `PostToolUse` 处理输出。
- MCP `output_token_limit` 在 Hub 原始输出和 Core hook 后结果各执行一次，最终仍受全局结果上限约束。
- 工具结果过大时进入 spill/压缩视图，canonical 记录保留与协议一致的 call/output 身份。

---

## 10. 测试要求

- 每个注册 `ToolEntry` 必须有同身份 `CoreToolRuntime`；
- 重复原生 `(namespace, name)`、缺失 runtime 和非法参数必须 fail closed；
- Deferred 工具只有在完成的 `ToolSearchOutput` 中出现后才进入下一 Step；
- MCP 普通工具和 broker 均可构建 Router 路由并保留审批、annotation 与输出预算；
- Skill `astro_tools` 按当前 Step 配置解析，不使用跨 Session 缓存；
- 只有 `load/view` 激活 toolset，且激活不能扩大 permission profile。
